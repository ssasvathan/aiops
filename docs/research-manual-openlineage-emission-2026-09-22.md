# Research: Emitting OpenLineage Events and Facets Ourselves

> **Audience:** Architecture reviewers of the DQ/lineage proposal. Also engineers and LLM agents who
> will decide where OpenLineage instrumentation lives.
>
> **Question:** Our frameworks — Spark (via the Spark–Snowflake connector), dbt, Airflow, and a Kafka
> ingestion platform called **E2** — may not emit the OpenLineage events or facets we want. What are
> the *supported* ways to emit them ourselves, and what does each cost?
>
> **Key framing:** separate (a) things we enable **once** at the platform level, in shared config
> (a listener jar + config, an Airflow plugin, a dbt package) from (b) things that require code in
> **every job owned by another team**. The ranking in §6 is the deliverable.
>
> **Scope:** Architecture proposal input only. No implementation.
>
> **Date:** 2026-09-22. **Status:** Draft for review.

## 1. Client APIs: emitting events by hand

### 1.1 The minimum valid RunEvent

The schema is `OL/spec/OpenLineage.json`, `$id = https://openlineage.io/spec/2-0-2/OpenLineage.json`.
A `RunEvent` is `allOf [BaseEvent, {...}]`:

| Field | Required by | Notes |
|---|---|---|
| `eventTime` | `BaseEvent.required` | `format: date-time` |
| `producer` | `BaseEvent.required` | `format: uri` — "URI identifying the producer of this metadata. For example this could be a git url with a given tag or sha" |
| `schemaURL` | `BaseEvent.required` | `format: uri`, points at the spec version |
| `run` | `RunEvent.required` | object with **`runId`** (`format: uuid`) required |
| `job` | `RunEvent.required` | object with **`namespace`** and **`name`** both required |
| `eventType` | **not in `required`** | enum `START \| RUNNING \| COMPLETE \| ABORT \| FAIL \| OTHER` |

**Correction to the premise worth flagging:** `eventType` is *not* listed in the JSON Schema
`required` array for `RunEvent` — only `run` and `job` are, plus the three `BaseEvent` fields. But
its own description is normative prose: *"It is required to issue 1 START event and 1 of [ COMPLETE,
ABORT, FAIL ] event per run. Additional events with OTHER eventType can be added to the same run.
For example to send additional metadata after the run is complete"*
(`OL/spec/OpenLineage.json`, `$defs.RunEvent`). So: schema-optional, protocol-required. A
schema-validating gateway will *not* reject an event missing `eventType`; a consumer building run
state will. (inference)

`inputs` / `outputs` are optional arrays of `InputDataset` / `OutputDataset`; each `Dataset`
requires `namespace` + `name` (`OL/spec/OpenLineage.json`, `$defs.Dataset`).

### 1.2 Minimal Python example (from the docs)

`OL/website/docs/client/python/usage.md` (= openlineage.io/docs/client/python/usage) gives the
canonical hand-rolled emission:

```python
from openlineage.client import OpenLineageClient
from openlineage.client.event_v2 import Dataset, Job, Run, RunEvent, RunState
from openlineage.client.uuid import generate_new_uuid
from datetime import datetime, timezone

client = OpenLineageClient()            # reads openlineage.yml / env vars
producer = "OpenLineage.io/website/blog"
job = Job(namespace="food_delivery", name="example.order_data")
run = Run(runId=str(generate_new_uuid()))

client.emit(RunEvent(
    eventType=RunState.START,
    eventTime=datetime.now(timezone.utc).isoformat(),
    run=run, job=job, producer=producer,
))
client.emit(RunEvent(
    eventType=RunState.COMPLETE,
    eventTime=datetime.now(timezone.utc).isoformat(),
    run=run, job=job, producer=producer,
    inputs=[Dataset(namespace="food_delivery", name="public.inventory")],
    outputs=[Dataset(namespace="food_delivery", name="public.menus_1")],
))
```

Note the client fills `schemaURL` for you — it is not a constructor argument in the example.

`runId` should be a UUID; `OL/website/docs/spec/object-model.md:69`: *"Each run will have a uniquely
identifiable `runId` that is generated by the client as UUID. The client is responsible for
maintaining the `runId` between different Run State Updates in the same Run. It is recommended to use
UUIDv7 format."* `generate_new_uuid()` is UUIDv7; there is also
`generate_static_uuid(instant, data)` which is **deterministic** — *"Calling function with same
arguments always produces the same result"* (`OL/client/python/src/openlineage/client/uuid.py`). That
determinism is the hook for §4.

### 1.3 Minimal Java example (from the docs)

`OL/website/docs/client/java/usage.md`:

```java
OpenLineageClient client = OpenLineageClient.builder()
    .transport(new ConsoleTransport()).build();     // or Clients.newClient() to use openlineage.yml

OpenLineage ol = new OpenLineage(URI.create("producer"));
UUID runId = UUIDUtils.generateNewUUID();
Run run = ol.newRunBuilder().runId(runId).facets(runFacets).build();
Job job = ol.newJobBuilder().namespace("namespace").name("jobName").facets(jobFacets).build();
client.emit(event);
```

`Clients.newClient()` reads `openlineage.yml`. The Java builder API is generated from the spec, so
core facets are typed builders (`ol.newNominalTimeRunFacetBuilder()...`).

### 1.4 Transports

Python transports shipped in `OL/client/python/src/openlineage/client/transport/`: `http`,
`async_http`, `kafka`, `file`, `console`, `composite`, `transform`, `noop`, plus vendor ones
(`datadog`, `gcplineage`, `amazon_datazone`, `msk_iam`). Java transports in
`OL/client/java/src/main/java/io/openlineage/client/transports/`: `Http`, `Kafka`, `File`, `Console`,
`Composite`, `Transform`, `Noop`.

Config (from `OL/website/docs/client/python/configuration.md`):

- **http** — `type: http`, `url` (required), `endpoint` (default `api/v1/lineage`), `timeout`
  (default 5s), `verify`, `auth` (`api_key` / `jwt` / `oauth2` / FQCN of a TokenProvider),
  `compression: gzip`, `custom_headers`, `retry` (`total: 5`, `backoff_factor: 0.3`,
  `status_forcelist: [500,502,503,504]`, `allowed_methods: ["HEAD","POST"]`). Behaviour: JSON POST,
  blocking, **raises on failure**.
- **kafka** — `type: kafka`, `topic`, `config` (a confluent-kafka producer dict), `flush`
  (default true), `messageKey`. Requires `pip install openlineage-python[kafka]`. Default message
  key is `run:{rootJob.namespace}/{rootJob.name}` when a parent facet with `root` exists, else
  `run:{parentJob...}`, else `run:{job.namespace}/{job.name}`. The docs say: *"It is recommended to
  provide `messageKey` if Job hierarchy is used. It can be any string, but it should be the same for
  all jobs in hierarchy, like `Airflow task -> Spark application -> Spark task runs`."* — i.e. Kafka
  partition ordering is only guaranteed within a key, so hierarchy-consistent keys matter for us.
- **file** — `type: file`, `log_file_path`, `append`, plus fsspec `storage_options` for
  s3/gcs/abfs/hdfs. Docs call it *"Designed mainly for integration testing"*.
- **console** — prints events. **This is the silent default**: `_resolve_transport` step 6 in
  `OL/client/python/src/openlineage/client/client.py` logs `"Couldn't find any OpenLineage transport
  configuration; will print events to console."` and returns `ConsoleTransport`. A misconfigured job
  therefore *looks* healthy and emits nothing. (inference: this is the single most likely silent
  failure mode of a per-job-configured rollout.)
- **composite** — `transports` (list or map), `continue_on_failure` (default true),
  `continue_on_success` (default true), `sort_transports` + per-transport `priority`. This is how we
  dual-write to Marquez *and* our own endpoint, or fail over.

**Configuration precedence** (`client.py`, `config` property docstring): (1) config dict passed to
the constructor, (2) YAML file — `$OPENLINEAGE_CONFIG`, then `./openlineage.yml`, then
`$HOME/.openlineage/openlineage.yml`, (3) env vars prefixed `OPENLINEAGE__` (`DYNAMIC_ENV_VARS_PREFIX`),
double-underscore-nested and JSON-parsed, e.g.
`OPENLINEAGE__TRANSPORT__TYPE=kafka`, `OPENLINEAGE__TRANSPORT__CONFIG='{"bootstrap.servers":...}'`.
Legacy `OPENLINEAGE_URL` / `OPENLINEAGE_API_KEY` / `OPENLINEAGE_ENDPOINT` are aliased into the
`OPENLINEAGE__TRANSPORT__TRANSPORTS__DEFAULT_HTTP__*` keys by `_alias_env_vars()`.
`OPENLINEAGE_DISABLED=true` → `NoopTransport`.

**Custom transports are a supported extension point**: `DefaultTransportFactory._create_transport`
(`OL/client/python/src/openlineage/client/transport/factory.py`) resolves an unknown `type` string as
a dotted import path (`import_from_string`) and requires it to subclass `Transport` with a
`config_class` subclassing `Config`. So "emit to E2's own sink" can be a transport class name in
shared config rather than code in each job.

## 2. Custom facets

### 2.1 The mechanism

Facets hang off five extension points, all typed as open maps in the schema
(`OL/spec/OpenLineage.json`):

| Extension point | Schema path | Value type |
|---|---|---|
| `run.facets` | `$defs.Run.properties.facets` | `additionalProperties: RunFacet` |
| `job.facets` | `$defs.Job.properties.facets` | `additionalProperties: JobFacet` |
| `<dataset>.facets` | `$defs.Dataset.properties.facets` | `additionalProperties: DatasetFacet` |
| `inputs[].inputFacets` | `$defs.InputDataset` | `additionalProperties: InputDatasetFacet` |
| `outputs[].outputFacets` | `$defs.OutputDataset` | `additionalProperties: OutputDatasetFacet` |

Every one of these resolves to `BaseFacet`:

```json
"BaseFacet": {
  "description": "all fields of the base facet are prefixed with _ to avoid name conflicts in facets",
  "properties": {
    "_producer":  {"type": "string", "format": "uri"},
    "_schemaURL": {"type": "string", "format": "uri"}
  },
  "additionalProperties": true,
  "required": ["_producer", "_schemaURL"]
}
```

`additionalProperties: true` is what makes arbitrary custom facets *schema-valid*. `JobFacet` and
`DatasetFacet` additionally allow `_deleted: boolean` — *"set to true to delete a facet"*.

Python: subclass `BaseFacet` (an `attr.define` class) and override `_get_schema()` to set
`_schemaURL`; otherwise `_schemaURL` defaults to the `BaseFacet` schema URL, which
`OL/website/docs/spec/facets/custom-facets.md` explicitly calls legal: *"By default, if the facet
class did not specify its own schema URL, that value would be that of BaseFacet. From the view of
OpenLineage specification, this is legal."*

### 2.2 Naming convention and prefix

`OL/spec/OpenLineage.md:101-124` is the normative text:

> *"Custom facets must use a distinct prefix named after the project defining them to avoid collision
> with standard facets defined in the OpenLineage.json spec."*
>
> *"Naming of custom facets should follow the pattern `{prefix}{name}{entity}Facet` PascalCased. …
> When attached to a core entity, the key should follow the pattern `{prefix}_{name}`, where both
> prefix and name are in camelCase. An example of a valid name is `BigQueryStatisticsJobFacet` and
> key is `bigQuery_statistics`."*

Also: *"The versioned URL must be an immutable pointer to the version of the facet schema. For
example, it should include a tag of a git sha and not a branch name."* — so `_schemaURL` should point
at a pinned commit of whatever repo holds our facet JSON schemas, not `main`.

Facet replacement semantics, same file (`OL/spec/OpenLineage.md:97`): *"A facet is an atomic piece of
metadata identified by its name. This means that emitting a new facet with the same name for the same
entity replaces the previous facet instance for that entity entirely."*

### 2.3 Is there a registry?

Yes, partially built. `OL/spec/registry/` contains `core/registry.json`, `iceberg/registry.json`,
`gcp/{lineage,composer,dataproc}/registry.json`. Core facets are addressed as
`ol:core:SchemaDatasetFacet.json` etc. The design is `OL/proposals/2161/registry.md`: *"Each consumer
or producer entity can claim a name, defined in the registry"*, with `CODEOWNERS` delegation per
`spec/registry/{Name}/` folder and CI consistency checks. There is **no registry page in
`website/docs/spec/`** (grep for "registry" under `website/docs/spec/` returns nothing), so
registering is optional in practice and unenforced for third parties. (inference: we can adopt the
`{prefix}_{name}` key convention without upstreaming anything; registering only buys collision
protection and generated docs.)

### 2.4 What consumers do with facets they don't recognise

`OL/website/docs/spec/facets/custom-facets.md`:

> *"as long as they follow the BaseFacet to contain the two mandatory element `_producer` and
> `_schemaURL`, it will be accepted and stored as part of the OpenLineage event, and will be able to
> be retrieved when you query those events."*
>
> *"Custom facets are not part of the default facets. Therefore, it will be treated as a payload data
> as-is, but applications retrieving those, if they have the capability to understand its structure
> and use them, should be able to do so without any problems."*

Store-and-ignore. The doc's worked example (`my_facet` on a run) shows it surfacing in Marquez's UI.

## 3. Emitting extra facets from *within* an existing integration

This is the section that decides the ranking. "Separate events" (§1) is always available and always
the worst option for correlation (§4); the question is what each integration lets us hook.

### 3(a) Spark — ServiceLoader + CustomFacetBuilder

`OL/website/docs/integrations/spark/extending.md` documents the extension surface.

**Entrypoint:** `OpenLineageEventHandlerFactory`. *"Custom implementations are registered by
following Java's ServiceLoader conventions. A file called
`io.openlineage.spark.api.OpenLineageEventHandlerFactory` must exist in the application or jar's
`META-INF/service` directory. Each line of that file must be the fully qualified class name of a
concrete implementation."*

The factory's default methods let us contribute, per `OpenLineageContext`:

- `createRunFacetBuilders` / `createJobFacetBuilders`
- `createInputDatasetFacetBuilders` / `createOutputDatasetFacetBuilders` / `createDatasetFacetBuilders`
- `createInput/OutputDatasetQueryPlanVisitors` and `createInput/OutputDatasetBuilder`

`CustomFacetBuilder` implements `BiConsumer`, accepting *"the valid input argument, and a
`BiConsumer<String, Facet>` consumer, which accepts the name and value of any custom facet that
should be attached to the OpenLineage run. There is no limit to the number of facets that can be
reported by a given CustomFacetBuilder. Facet names that conflict will overwrite previously reported
facets if they are reported for the same Spark event."*

Builders can be defined for: `SparkListenerSQLExecutionStart`, `SparkListenerSQLExecutionEnd`,
`SparkListenerJobStart`, `SparkListenerJobEnd`, `RDD`, `Stage`, `StageInfo`, `ActiveJob`.

> **Cost:** one jar, on the Spark classpath, plus the listener config. **Zero per-job code.** This is
> the strongest "enable once" lever we have. Deployment = the jar joins whatever mechanism already
> puts `openlineage-spark` on the cluster.

**Config-only facet levers (no jar at all)**, from
`OL/website/docs/integrations/spark/configuration/spark_conf.md`:

| Config | Effect |
|---|---|
| `spark.openlineage.facets.custom_environment_variables` | List of env vars captured into the `environment-properties` facet. Implemented by `CustomEnvironmentFacetBuilder` (`OL/integration/spark/shared/.../facets/builder/CustomEnvironmentFacetBuilder.java`), which emits facet key `"environment-properties"` holding `{envVar: System.getenv(envVar)}`. The Java client field is `FacetsConfig.customEnvironmentVariables`, JSON property `custom_environment_variables` (`OL/client/java/.../transports/FacetsConfig.java:36`). The Spark conf table also lists `spark.openlineage.facets.variables`. |
| `spark.openlineage.capturedProperties` | Comma-separated Spark properties captured into the spark properties facet (default `spark.master`, `spark.app.name`) |
| `spark.openlineage.job.tags` / `spark.openlineage.run.tags` | `key:value` pairs, `;`-separated → tag facets |
| `spark.openlineage.job.owners.<ownership-type>` | job ownership facet |
| `spark.openlineage.facets.<facet name>.disabled` | per-facet kill switch; `debug`, `spark.logicalPlan`, `spark_unknown` are disabled by default |
| `spark.openlineage.parentJobNamespace` / `parentJobName` / `parentRunId` / `rootParent*` | drive the `ParentRunFacet` (see §4) |

**Dataset-level facets with no code at all**, for DataSourceV2 connectors
(`OL/website/docs/integrations/spark/extending.md`): `openlineage-spark` reads the
`DataSourceV2Relation`'s `Table` properties map for `openlineage.dataset.name`,
`openlineage.dataset.namespace`, and *"Properties can be also used to pass any dataset facet. For
example: `openlineage.dataset.facets.customFacet={"property1": "value1", ...}`"*, and *"Custom facets
are automatically filled with `_producer` field."* Whether the Spark–Snowflake connector exposes a
`DataSourceV2Relation` with a settable properties map here is **[UNVERIFIED]** — OpenLineage ships a
dedicated `integration/spark/vendor/snowflake/` `SnowflakeRelationVisitor` instead, which suggests
the connector is handled via the v1 relation path. (inference)

There is also a shaded, connector-author-facing API in
`OL/integration/spark-extension-interfaces/` (`LineageRelationProvider`, `InputLineageNode`,
`OutputLineageNode`, `InputDatasetWithFacets`, `OutputDatasetWithFacets`,
`SparkOpenLineageExtensionVisitor`) — that is for us only if we fork/patch a connector, not for
adding facets to someone else's job.

### 3(b) Airflow — yes, and there is a platform-wide hook

Three tiers, in the provider's own precedence order
(`AF/providers/openlineage/docs/guides/developer.rst`, "Extraction precedence"):
1. a registered custom **Extractor** for the operator class name;
2. **OpenLineage methods** on the operator (`DefaultExtractor`);
3. **Hook-level lineage** (merged when 1/2 return no datasets);
4. inlets/outlets, *"only consulted as a last resort"*.

**Per-operator methods** (requires owning or forking the operator):

```python
def get_openlineage_facets_on_start() -> OperatorLineage: ...
def get_openlineage_facets_on_complete(ti: TaskInstance) -> OperatorLineage: ...
def get_openlineage_facets_on_failure(ti: TaskInstance) -> OperatorLineage: ...
```

called on RUNNING / SUCCESS / FAILED respectively; at least one of `on_start` / `on_complete` must
exist. `OperatorLineage` is `{inputs, outputs, run_facets: dict[str, RunFacet], job_facets: dict[str,
BaseFacet]}` and *"OpenLineage integration itself takes care to enrich it with things like general
Airflow facets, proper event time and type, creating proper OpenLineage RunEvent."*

**Custom Extractors** (no operator fork, but per-operator-class):
subclass `BaseExtractor`, implement `_execute_extraction` and `get_operator_classnames`, register via

```ini
[openlineage]
extractors = full.path.to.ExtractorClass;full.path.to.AnotherExtractorClass
```

(`AIRFLOW__OPENLINEAGE__EXTRACTORS`). Caveat from the docs: *"any import from Airflow can be
unnoticeably cyclical … import from Airflow only locally"*.

**The platform-wide, zero-per-DAG hook — `custom_run_facets`**
(`AF/providers/openlineage/docs/configurations-ref.rst`, §Custom Facets):

> *"You can also inject your own custom facets in the lineage event's run facet using the
> `custom_run_facets` Airflow configuration. … Airflow OpenLineage listener will automatically
> execute these functions during the lineage event generation and append their return values to the
> run facet in the lineage event."*

```ini
[openlineage]
custom_run_facets = full.path.to.get_my_custom_facet;full.path.to.another_custom_facet_function
```

Signature: `(task_instance: TaskInstance, ti_state: TaskInstanceState) -> dict[str, RunFacet] | None`.
Facets must inherit `RunFacet` *"for the `_producer` and `_schemaURL` to be automatically added"*.
Documented behaviour notes:

- *"executed both at the START and COMPLETE/FAIL of the TaskInstance and added to the corresponding
  OpenLineage event"*;
- use the second argument, not `ti.current_state()`, because *"the OpenLineage listener may get
  called before the TaskInstance's state is updated in Airflow database"*;
- *"When path to a single function is registered more than once, it will still be executed only
  once"*;
- *"When duplicate custom facet keys are returned by multiple functions registered, the result of
  random function result will be added to the lineage event."* — so our functions must own disjoint
  keys.

**Limitation:** `custom_run_facets` adds **run** facets only. There is no equivalent
`custom_job_facets` / `custom_dataset_facets` option in `AF/providers/openlineage/provider.yaml`
(full option list: `config_conn_id`, `config_path`, `custom_run_facets`,
`dag_state_change_process_pool_size`, `debug_mode`, `disable_source_code`, `disabled`,
`disabled_for_operators`, `emission_policy`, `execution_timeout`, `execute_in_thread`, `extractors`,
`include_full_task_info`, `namespace`, `selective_enable`, `spark_inject_parent_job_info`,
`spark_inject_transport_info`, `transport`). Job/dataset facets require an Extractor or operator
methods.

**Two more platform-wide switches that matter for us**
(`AF/providers/openlineage/provider.yaml`, both default `False`;
`AF/providers/openlineage/docs/spark.rst`):

- `spark_inject_parent_job_info` — *"Automatically inject OpenLineage's parent job (namespace, job
  name, run id) information into Spark application properties for supported Operators."*
- `spark_inject_transport_info` — same for transport config.

Supported operators listed in `spark.rst`: `EmrAddStepsOperator`, `EmrContainerOperator`,
`EmrServerlessStartJobOperator`, `GlueJobOperator`, `LivyOperator`, `SparkSubmitOperator`,
`DatabricksRunNowOperator`, `DatabricksSubmitRunOperator`, `DataprocCreateBatchOperator`,
`DataprocInstantiateInlineWorkflowTemplateOperator`, `DataprocSubmitJobOperator`. *"This eliminates
the need to manually configure these properties in every Spark operator."* The per-DAG alternative is
the macros (`AF/providers/openlineage/docs/macros.rst`):
`macros.OpenLineageProviderPlugin.lineage_job_namespace()`, `lineage_job_name(task_instance)`,
`lineage_run_id(task_instance)`, `lineage_root_*`, `lineage_parent_id(task_instance)` — templated
into `spark.openlineage.parentJobNamespace` etc.

### 3(c) dbt — read-only artifact parsing; no facet plugin point

`OL/website/docs/integrations/dbt.md` describes two modes:

1. **Artifact Processor (post-run)** — parses `target/manifest.json`, `target/run_results.json`, and
   optionally `target/catalog.json`. Paths are built in
   `OL/integration/common/src/openlineage/common/provider/dbt/local.py:103-105`; the target dir
   resolution order is *"user-defined target_path > env var > dbt_project.yml > default"* (default
   `"target"`). *"if a `dbt run` executes 5 models, the Artifact Processor will emit 10 OpenLineage
   events (5 START events followed by 5 COMPLETE/FAIL events)."*
2. **Structured Log Processor (real-time)** — `dbt-ol run --consume-structured-logs`, streaming dbt's
   JSON log lines. Docs note the artifact mode *"only retains the last adapter response / query ID
   for a node, dropping earlier queries"*, while structured logs *"captures all sequential SQL
   queries"*.

Facets emitted (from the same page): job `jobType`, job `dbt_node_metadata`, run `dbt_version`, run
`dbt_run`, dataset `symlink_identifiers`, dataset `documentation`; optionally run `parent`, dataset
`schema` (needs `catalog.json`), dataset `dbt_model`, job `sql`, dataset `columnLineage`, dataset
`dbt_exposures`. Facet classes: `OL/integration/common/src/openlineage/common/provider/dbt/facets.py`.

**Can a dbt package / `on-run-end` hook emit OL events?** Not through any documented OpenLineage
mechanism. `openlineage-dbt` is a *wrapper process* (`dbt-ol` → `openlineage.dbt:main`, console
script in `OL/integration/dbt/pyproject.toml`) that shells out to dbt and then reads artifacts. A
grep across `OL/integration/dbt/src/` and `OL/integration/common/src/` finds **no** `entry_points`,
plugin registry or `ServiceLoader`-equivalent — there is no supported way to inject a facet builder
into `openlineage-dbt`. A dbt `on-run-end` hook runs *SQL in the warehouse*, so it could at most
write a table; emitting an OL HTTP/Kafka event from it is not possible without an external process.
**[UNVERIFIED]** that any dbt-side hook can emit OL events; no primary source describes one.

**What we *can* do from dbt YAML with zero Python:** node `meta` and `tags` are read into a
`TagsRunFacet`. `OL/integration/common/.../dbt/processor.py:1016-1026`: *"Plain dbt `tags` keep
`source="DBT"` and value `"true"`; each `meta` entry becomes a"* tag with `source="DBT_META"`. So
arbitrary key/values set in `schema.yml` `meta:` reach OpenLineage as run tags — flattened to
strings, not a structured custom facet, but it is a real, per-model-YAML-only channel. (inference:
this is the cheapest dbt-side metadata path, at the cost of per-model YAML edits by the model owner.)

### 3(d) E2 (Kafka ingestion) — nothing exists; hand-emission is the only option

`OL/integration/` contains exactly: `common`, `dbt`, `flink`, `hive`, `hive-docker`, `spark`,
`spark-docker`, `spark-extension-entrypoint`, `spark-extension-interfaces`, `sql`. There is no
Kafka-Connect, Kafka-Streams-generic or "streaming ingestion platform" integration. So for E2 the
only supported route is §1 — the Java or Python client, called from E2's own control plane.
(inference: because E2 is *ours*, this is still a platform-level change — one emitter in the E2
framework, zero work for the teams that define E2 pipelines. It lands in bucket (a), not (b).)

## 4. Consistency risks of hand-emitted events

### 4.1 Same `runId` events are *merged*, not replaced

`OL/website/docs/spec/object-model.md`: *"Subsequent updates are additive: input Datasets, for
example, can be specified along with START, along with COMPLETE, or both. This accommodates situations
where information is only available at certain times."* Combined with the facet rule from
`OL/spec/OpenLineage.md:97` (*"emitting a new facet with the same name for the same entity replaces
the previous facet instance for that entity entirely"*), the model is: **events accumulate, facets
overwrite by key.**

Consequence for us: a *separate* `OTHER` event carrying only `{eventTime, producer, schemaURL, run:
{runId, facets: {ourFacet}}, job: {namespace, name}}` is the sanctioned way to bolt a facet onto an
existing run. The spec explicitly blesses it: *"Additional events with OTHER eventType can be added
to the same run. For example to send additional metadata after the run is complete"*
(`OL/spec/OpenLineage.json`, `RunEvent.eventType` description).

**Risk:** we must send only the facets we own. Sending a partially-populated `job.facets` or an empty
`inputs: []` is fine (additive), but re-sending a facet key the framework also sets will clobber the
framework's version — last writer wins, with no ordering guarantee across two independent producers.
(inference)

### 4.2 Attaching a facet to a run the framework created — the runId problem

You need the framework's `runId`. Options, in descending reliability:

- **Airflow: recompute it.** The provider derives run IDs deterministically
  (`AF/providers/openlineage/src/airflow/providers/openlineage/utils/utils.py:1469-1527`):
  ```python
  build_task_instance_ol_run_id = generate_static_uuid(
      instant=logical_date,
      data=f"{conf.namespace()}.{dag_id}.{task_id}.{try_number}.{map_index}".encode())
  build_dag_run_ol_run_id = generate_static_uuid(
      instant=logical_date,
      data=f"{conf.namespace()}.{dag_id}.{clear_number}".encode())
  ```
  Exposed as `OpenLineageAdapter.build_task_instance_run_id` / `build_dag_run_id`
  (`AF/providers/openlineage/src/airflow/providers/openlineage/plugins/adapter.py:145-157`) and via
  the `lineage_run_id(task_instance)` macro. So an out-of-band emitter *can* reconstruct the exact
  runId — but it depends on `conf.namespace()`, `try_number` and `map_index`, and on the provider not
  changing the recipe. **This is a private-ish coupling**: `generate_static_uuid`'s own docstring says
  *"UUID version is an implementation detail, and should not be relied on."* (inference: treat
  recomputation as a supported-but-brittle path; prefer `custom_run_facets`, which runs inside the
  listener and needs no runId at all.)
- **Spark: we cannot recompute it.** `spark.openlineage.applicationRunId` lets us *override* it
  (*"Custom value overwriting Spark app run id in events"*, `spark_conf.md`) — which turns the
  problem around: we supply the id. But per-Spark-*action* run ids are generated internally. A
  `CustomFacetBuilder` inside the listener sidesteps this entirely.
- **dbt: we cannot recompute it.** `openlineage-dbt` generates node run ids internally per node; the
  job names are `{database}.{schema}.{table}`-ish (`processor.py:345-352,458`) but the run ids are
  fresh UUIDs. An out-of-band dbt facet emitter would have to correlate on job name + time window,
  not runId. (inference)

### 4.3 Parent run facet

The parent chain is how a hand-emitted event joins the graph without guessing a runId. Mechanisms:

- **Airflow → task**: automatic. *"TaskInstance events automatically include a ParentRunFacet that
  references the originating DAG run as parent job. User Action Required: None."*
  (`AF/providers/openlineage/docs/macros.rst`)
- **Airflow → Spark**: `spark.openlineage.parentJobNamespace` / `parentJobName` / `parentRunId`, plus
  `rootParent*` (Spark integration ≥ 1.31.0). Set once via `spark_inject_parent_job_info=True`, or
  per-DAG via macros.
- **Airflow → triggered DAG**: `TriggerDagRunOperator` injects it automatically since
  `apache-airflow-providers-standard==1.10.0`; disable with `openlineage_inject_parent_info=False`.
- **API-triggered DAG**: `conf.openlineage.{parentRunId,parentJobName,parentJobNamespace,
  rootParentRunId,rootParentJobName,rootParentJobNamespace}`. Warning from the docs: *"If any of the
  three parent fields are missing, no parent facet will be created. Partial or mixed configurations
  are not supported."*
- **→ dbt**: `OPENLINEAGE_CONTEXT` env var, JSON `{"parent": {"run": {"runId": ...}, "job":
  {"namespace":..., "name":...}, "root": {...}}}`, or legacy
  `OPENLINEAGE_PARENT_ID="namespace/job_name/run_id"` (3 slash-separated parts;
  `OL/integration/common/.../dbt/utils.py:124-215`). Malformed values are logged and ignored, never
  raised — *"Received OPENLINEAGE_PARENT_ID but can't parse it"*. If `root` is absent, root defaults
  to parent.

**This is the cheapest correlation mechanism available to us**: an environment variable or a Spark
conf, set once in the platform's job-submission layer, not per job. (inference)

### 4.4 Event ordering

Nothing in the spec guarantees ordering. Specific exposures:

- HTTP transport is blocking and retries `[500,502,503,504]` up to 5 times with backoff — so a
  retried START can arrive after a COMPLETE emitted by a *different* process. (inference)
- `async_http` explicitly decouples emission from the call.
- Kafka: ordering holds only within a partition, i.e. within a `messageKey`. Hence the docs'
  recommendation to use a hierarchy-stable key.
- Airflow: `execute_in_thread` (provider option) runs task-level emission in a time-bounded thread,
  and `execution_timeout` caps extraction — both can drop events under load. (inference: a dropped
  START plus a delivered facet-only `OTHER` event yields a run the consumer has facets for but no
  start time.)

### 4.5 The `_producer` field is our audit trail

Because facets overwrite by key and two producers can write the same run, `_producer` (a URI, ideally
a git URL with a sha per the schema's own example) is the only way to attribute a facet after the
fact. Set it to a pinned internal URL per emitter. (inference)

## 5. What consumes them

### 5.1 If we emit only to our own HTTP/Kafka endpoint (no Marquez)

Nothing in the producer side breaks. The client's only contract with the HTTP endpoint is: POST JSON
to `{url}/{endpoint}` (default endpoint `api/v1/lineage`) and return a non-error status. Behaviour on
failure: *"Events are sent immediately and the call blocks until completion. Uses httpx2 with
built-in retry support and **raises exceptions on failure**"*
(`OL/website/docs/client/python/configuration.md`, HTTP Transport §Behavior). So our endpoint must
return 2xx, and must not return 500/502/503/504 unless it wants 5 retries.

Things we lose by not running Marquez, all of which are *consumer* features, not protocol features:
run-state assembly, the graph UI, and dataset versioning. The docs' custom-facet walkthrough uses
Marquez only to *display* the custom facet.

Kafka-only is equally fine — `KafkaTransport` just serialises to JSON and produces to a topic. Note
the Airflow caveat: *"a Kafka producer needs to be created for each OpenLineage event. It happens due
to the Airflow execution and plugin model, which requires us to send messages from worker processes.
These are created dynamically for each task execution."* That is a real per-task connection cost for
an Airflow + Kafka transport combination.

### 5.2 Is anything validated?

**Essentially nothing, by default.** Evidence:

- The Python client does not validate against the JSON schema before emitting — `serde.py` and
  `http.py` contain no `jsonschema`/validate call. It serialises attrs objects and POSTs them.
- The custom-facet doc's position is store-as-is (§2.4).
- OpenLineage's own answer to this gap is an opt-in proxy: `OL/proxy/fluentd/README.md` says modern
  collectors *"have great potential except for a single missing feature: **the ability to parse and
  validate OpenLineage events at the point of HTTP input**. This is important as one would like to
  get a `Bad Request` response immediately when sending invalid OpenLineage events to an endpoint."*
  and they wrote a Fluentd parser plugin for exactly that, noting *"the Fluentd integration can be
  also used as a OpenLineage HTTP validation backend for development purposes."* It is flagged
  *"experimental and could be changed or removed in a future release."*
- `OL/spec/tests/` holds per-facet test fixtures (`ColumnLineageDatasetFacet/`,
  `DataQualityMetricsInputDatasetFacet/`, …) — CI validation of the *spec*, not of our traffic.

**Implication for the proposal:** if we want our custom facets to be schema-checked, *we* build that
— either a validating handler at our HTTP ingest, or a schema check in a Kafka consumer. Nothing
upstream will catch a typo'd facet key or a missing `_producer`. (inference)

## 6. Ranking by per-job cost (the conclusion)

**Tier 0 — enable once, zero code and zero config in anyone else's job.**

| Lever | Where it is set | Buys |
|---|---|---|
| Spark `OpenLineageEventHandlerFactory` jar (ServiceLoader) | platform Spark image / classpath | arbitrary run/job/dataset/input/output custom facets on **every** Spark job, from Spark's own listener events |
| Airflow `[openlineage] custom_run_facets` | `airflow.cfg` / `AIRFLOW__OPENLINEAGE__CUSTOM_RUN_FACETS` | arbitrary **run** facets on every task event, START and COMPLETE/FAIL |
| Airflow `spark_inject_parent_job_info` / `spark_inject_transport_info` | `airflow.cfg` | Airflow↔Spark run correlation for 11 listed operators, *"eliminates the need to manually configure these properties in every Spark operator"* |
| OL client config via `OPENLINEAGE__*` env vars or `openlineage.yml` | platform env / image | transport (incl. `composite` dual-write), `facets.environment_variables`, `tags.job` / `tags.run`, `filters` — applied to every event the client emits |
| Spark `spark.openlineage.*` in shared defaults | `spark-defaults.conf` | `facets.custom_environment_variables`, `capturedProperties`, `job.tags`/`run.tags`, `job.owners`, per-facet disable |
| E2: one OL emitter in the E2 framework itself | E2 platform code | full events for Kafka ingestion; pipeline authors do nothing |
| `OPENLINEAGE_CONTEXT` / `OPENLINEAGE_PARENT_ID` for dbt | job-submission layer | parent-run correlation for every dbt invocation |

**Tier 1 — enable once, but per-*operator-class* or per-connector work, still no job-owner work.**

| Lever | Cost |
|---|---|
| Airflow custom `Extractor` + `[openlineage] extractors` | one class per operator class we care about; the only route to **job** and **dataset** facets platform-wide; beware cyclical Airflow imports |
| Spark `QueryPlanVisitor` / `Input`/`OutputDatasetBuilder` in the same jar | one visitor per logical-plan node type (e.g. a Snowflake relation) |
| `openlineage.dataset.facets.<name>` via DataSourceV2 table properties | needs the connector to expose the properties map; **[UNVERIFIED]** for spark-snowflake |

**Tier 2 — per-artifact edits by the owning team, but declarative (YAML), not code.**

| Lever | Cost |
|---|---|
| dbt node `meta:` / `tags:` in `schema.yml` → `TagsRunFacet` (`source="DBT_META"`) | one YAML block per model, values flattened to strings |
| Airflow DAG-run `conf.openlineage.{parent,root}*` for API-triggered DAGs | per trigger call; all three parent fields or none |
| Airflow macros (`lineage_run_id` etc.) templated into Spark operator `conf` | per operator instance — **only needed if `spark_inject_parent_job_info` cannot be used** |

**Tier 3 — code in every job owned by another team. Avoid.**

| Lever | Cost |
|---|---|
| `get_openlineage_facets_on_start/_on_complete/_on_failure` on the operator | requires owning or forking the operator; fine for *our* operators, a non-starter for third-party ones (the docs themselves route that case to custom Extractors) |
| Hand-emitted `RunEvent`s from inside job code via `openlineage-python` / `-java` | every job owner writes emit calls, manages runIds, and must not mis-set the transport — and a missing transport config silently falls back to `ConsoleTransport` |
| Out-of-band `OTHER` events keyed on a recomputed Airflow runId | no per-job code, but couples us to a `generate_static_uuid` recipe the client docstring calls *"an implementation detail … should not be relied on"* |

**Headline findings for the proposal:**

1. **Three of our four frameworks have a true Tier-0 facet hook.** Spark (ServiceLoader +
   `CustomFacetBuilder`) and Airflow (`custom_run_facets`) both let a platform team add custom facets
   to every job with no job-owner involvement. E2 is ours, so it is Tier 0 by construction.
2. **dbt is the odd one out.** `openlineage-dbt` has no plugin point — it is a wrapper that parses
   `manifest.json` / `run_results.json` / `catalog.json` after the fact. Our only zero-code-per-job
   dbt levers are the client-level config (tags, env-var facet, transport) and parent-run env vars;
   anything model-specific costs a `meta:` block in each model's YAML.
3. **Airflow's platform hook is run-facets-only.** If the proposal needs job or dataset facets
   platform-wide from Airflow, that is a custom Extractor per operator class (Tier 1), not a config
   line.
4. **Prefer facets-inside-the-integration over separate events.** Separate events are spec-legal
   (`eventType: OTHER`, additive merge) but require obtaining the framework's `runId`, which is only
   reconstructible for Airflow, and only via a mechanism upstream warns not to rely on.
5. **Nothing validates our custom facets.** The client does not schema-check before emitting, and
   consumers are told to store unknown facets as-is. If we want validation, we build it at our own
   HTTP/Kafka ingest — OpenLineage's own answer is an experimental Fluentd parser plugin.
6. **Watch the console-transport default.** An unconfigured client prints to stdout and logs a
   warning rather than failing. Any per-job emission strategy needs a "did we actually emit" check;
   platform-level transport config removes the failure mode entirely.

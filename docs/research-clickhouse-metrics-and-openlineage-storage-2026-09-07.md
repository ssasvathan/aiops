## Current-State Anchor (repo context, one paragraph)

Today the pipeline exports OTLP metrics to an OpenTelemetry Collector that re-exposes them
on a Prometheus scrape endpoint, and Grafana reads Prometheus
(`config/otel-collector.yaml`: `receivers: [otlp] -> processors: [batch] -> exporters:
[prometheus]`; `docker-compose.yml` pins `otel/opentelemetry-collector-contrib:0.96.0`,
`prom/prometheus:v2.50.1`). Kafka is already in the stack with topics `aiops-case-header`
and `aiops-triage-excerpt`. Durable state is PostgreSQL; casefiles are in MinIO. Nothing in
the repo speaks ClickHouse today. The question this document answers is what the storage
design would look like if ClickHouse became the substrate for **both** dense metric series
and sparse OpenLineage data-quality (DQ) events.

**Immediate version finding, worth stating up front:** the collector image pinned in
`docker-compose.yml` is `0.96.0`. The ClickHouse exporter's metrics tables have taken at
least two breaking changes since then — `ServiceName` was added as a column to all metrics
tables in v0.98.0, and `AggTemp` was renamed to `AggregationTemporality` in v0.104.0
(see [§1.4](#14-is-the-schema-stable-across-versions)). Adopting the ClickHouse exporter
means moving the collector forward by ~64 minor versions, not enabling a flag.

## 1. What the OTel ClickHouse exporter actually creates for metrics

### 1.1 Where the DDL lives

The DDL is **no longer** in Go string constants in
`internal/{sum,gauge,histogram}_metrics.go`. As of the pinned tag it lives as `.sql`
templates under
[`exporter/clickhouseexporter/internal/sqltemplates/`](https://github.com/open-telemetry/opentelemetry-collector-contrib/tree/v0.160.0/exporter/clickhouseexporter/internal/sqltemplates),
one `*_table.sql` and one `*_insert.sql` per signal. The README confirms this is the
intended contract:

> "The default DDL used by the exporter can be found in `internal/sqltemplates`. Be sure to
> customize the indexes, TTL, and partitioning to fit your deployment. Column names and
> types must be the same to preserve compatibility with the exporter's `INSERT` statements."
> — [README.md @ v0.160.0, "Schema management"](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.160.0/exporter/clickhouseexporter/README.md#schema-management)

The `%s` placeholders are, in order: database, table, cluster clause, engine string, TTL
clause. Engine defaults to `MergeTree()`
([`config.go:277-287`, `defaultTableEngineName = "MergeTree"`](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.160.0/exporter/clickhouseexporter/config.go)),
and the TTL clause is generated by `GenerateTTLExpr`:

```go
// exporter/clickhouseexporter/internal/clickhouse.go @ v0.160.0
func GenerateTTLExpr(ttl time.Duration, timeField string) string {
	if ttl > 0 {
		switch {
		case ttl%(24*time.Hour) == 0:
			return fmt.Sprintf(`TTL %s + toIntervalDay(%d)`, timeField, ttl/(24*time.Hour))
		case ttl%time.Hour == 0:
			return fmt.Sprintf(`TTL %s + toIntervalHour(%d)`, timeField, ttl/time.Hour)
		case ttl%time.Minute == 0:
			return fmt.Sprintf(`TTL %s + toIntervalMinute(%d)`, timeField, ttl/time.Minute)
		default:
			return fmt.Sprintf(`TTL %s + toIntervalSecond(%d)`, timeField, ttl/time.Second)
		}
	}
	return ""
}
```

So `ttl: 72h` in exporter config yields `TTL TimeUnix + toIntervalDay(3)` — a plain
row-level `DELETE` TTL, nothing more. **The exporter cannot emit tiering or rollup TTL.**
That is a strong argument for `create_schema: false` (see [§8](#8-retention)).

Default table names come from `config.go`, **not** the README — and they disagree:

| Metric type | Default table (source of truth: `config.go`) |
|---|---|
| Gauge | `otel_metrics_gauge` |
| Sum | `otel_metrics_sum` |
| Summary | `otel_metrics_summary` |
| Histogram | `otel_metrics_histogram` |
| Exponential histogram | `otel_metrics_exponential_histogram` |

`config.go` defines `defaultExpHistogramSuffix = "_exponential_histogram"` and
`buildMetricTableNames()` concatenates `defaultMetricTableName + defaultExpHistogramSuffix`
([`config.go:101-110, 244-266`](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.160.0/exporter/clickhouseexporter/config.go)),
while the README's config reference says `otel_metrics_exp_histogram`
([README lines ~386, ~534](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.160.0/exporter/clickhouseexporter/README.md)).
**The README is stale at v0.160.0.** Trust the Go source. This is a small thing, but it is
exactly the kind of thing that breaks a dashboard on day one.

### 1.2 The real DDL (verbatim from `internal/sqltemplates`, tag v0.160.0)

All five tables share an identical head (resource/scope/metric identity), an identical
index block, and an identical engine/partition/order/settings tail. Only the value columns
differ. The tail, common to all five:

```sql
    ) ENGINE = %s
    %s
    PARTITION BY toDate(TimeUnix)
    ORDER BY (ServiceName, MetricName, toStartOfHour(TimeUnix), cityHash64(Attributes), TimeUnix)
    SETTINGS index_granularity=8192, ttl_only_drop_parts = 1
```

Note three things that matter for the design: **daily partitions**,
`ttl_only_drop_parts = 1` already set by default, and a sort key whose third element is
`toStartOfHour(TimeUnix)` with the raw `TimeUnix` only as the final tiebreaker. The
attribute set is folded into the sort key as `cityHash64(Attributes)` — an *opaque* hash, so
you can sort-key-prune on `(ServiceName, MetricName, hour)` and on an *exact whole-attribute-map
match*, but **not** on a single label. Single-label filtering falls back to the bloom filter
skip indices. The README says this explicitly:

> "A skip index on the map values lets a query that filters on a single attribute value
> prune granules, but because every value shares the same time-partitioned parts, a wide
> time-range read filtered to one value still scans granules that also contain other values'
> rows — the filter is applied after the granule is read." … "If you query a shared table by
> a *high-cardinality* attribute … set `create_schema: false` and manage the DDL yourself so
> the attribute participates in the primary key."
> — [README @ v0.160.0, "Reading a shared table by a resource attribute"](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.160.0/exporter/clickhouseexporter/README.md)

The common index block, also identical across all five:

```sql
    INDEX idx_res_attr_key mapKeys(ResourceAttributes) TYPE bloom_filter(0.01) GRANULARITY 1,
    INDEX idx_res_attr_value mapValues(ResourceAttributes) TYPE bloom_filter(0.01) GRANULARITY 1,
    INDEX idx_scope_attr_key mapKeys(ScopeAttributes) TYPE bloom_filter(0.01) GRANULARITY 1,
    INDEX idx_scope_attr_value mapValues(ScopeAttributes) TYPE bloom_filter(0.01) GRANULARITY 1,
    INDEX idx_attr_key mapKeys(Attributes) TYPE bloom_filter(0.01) GRANULARITY 1,
    INDEX idx_attr_value mapValues(Attributes) TYPE bloom_filter(0.01) GRANULARITY 1,
    INDEX idx_time_minmax TimeUnix TYPE minmax GRANULARITY 1
```

### 1.3 Attribute and exemplar layout, concretely

- **Attributes are `Map(LowCardinality(String), String)`**, in three flavours:
  `ResourceAttributes`, `ScopeAttributes`, `Attributes` (datapoint-level). `service.name` is
  additionally promoted to a top-level `ServiceName LowCardinality(String)` column.
- Access is `Attributes['topic']`. Missing key returns the type's default (empty string),
  not NULL — a classic footgun when distinguishing "label absent" from "label empty".
- **Exemplars are a `Nested` type**, which ClickHouse stores as parallel arrays. The
  exporter's INSERT proves it — it addresses the flattened array columns directly:

```sql
-- internal/sqltemplates/metrics_gauge_insert.sql @ v0.160.0
INSERT INTO "%s"."%s" (
    ResourceAttributes, ResourceSchemaUrl, ScopeName, ScopeVersion, ScopeAttributes,
    ScopeDroppedAttrCount, ScopeSchemaUrl, ServiceName, MetricName, MetricDescription,
    MetricUnit, Attributes, StartTimeUnix, TimeUnix, Value, Flags,
    Exemplars.FilteredAttributes,
    Exemplars.TimeUnix,
    Exemplars.Value,
    Exemplars.SpanId,
    Exemplars.TraceId) VALUES (?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?,?)
```

Reading an exemplar therefore means `ARRAY JOIN Exemplars.TraceId` or
`Exemplars.TraceId[1]`, not a struct access.

- **Codecs:** `Delta, ZSTD(1)` on the two `DateTime` columns and on monotonic counters
  (`Count`, `IsMonotonic`); plain `ZSTD(1)` everywhere else — including `Value Float64`.
  Notably the exporter does **not** use `Gorilla` or `DoubleDelta` on `Value`, even though
  ClickHouse ships both as time-series-oriented codecs
  ([CREATE TABLE / codecs](https://clickhouse.com/docs/sql-reference/statements/create/table)).
  If storage on dense float series matters, that is a tunable you get by owning the DDL.

### 1.4 Is the schema stable across versions?

**No, and the project says so.** Metrics are the *least* stable signal in this exporter:

```yaml
# exporter/clickhouseexporter/metadata.yaml @ v0.160.0
status:
  class: exporter
  stability:
    development: [profiles]
    alpha: [metrics]
    beta: [traces, logs]
```

Traces and logs graduated to `beta` (v0.109.0 and v0.98.0 respectively per the changelog);
**metrics are still `alpha`** at v0.160.0. Per the collector's own stability definitions,
`alpha` explicitly permits breaking changes
([component-stability.md](https://github.com/open-telemetry/opentelemetry-collector/blob/main/docs/component-stability.md#alpha)).
The README adds:

> "In some cases the table changes will not be backwards compatible. Be sure to check the
> changelog for breaking changes before upgrading your collector."

Real breaking changes affecting **metrics tables**, extracted from
[`CHANGELOG.md` @ v0.160.0](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.160.0/CHANGELOG.md)
by matching `clickhouseexporter` entries under `🛑 Breaking changes 🛑` headings:

| Version | Breaking change | Issue |
|---|---|---|
| v0.104.0 | "Add `AggregationTemporality` column to histogram and exponential histogram tables. **Rename `AggTemp` column to `AggregationTemporality`** in sum table." | #33424 |
| v0.98.0 | "Add ServiceName as `column` into Clickhouse metrics tables" | #31670 |
| v0.109.0 | "All metrics will remove the suffix `_seconds` … In some cases, like using `clickhouseexporter` (save data in native OTLP format), it will be a breaking change." | — |
| v0.109.0 | "Upgrade trace SpanKind and StatusCode string values" (traces) | #34799 |
| v0.107.0 | "Add `compress` option … with default value of `lz4`" | #34365 |
| v0.81.0 | "Add scopeName and scopeVersion column to span table" (traces) | #21214 |
| v0.71.0 | "use endpoint instead of raw dsn in configuration" | #8028 |

Non-breaking but schema-relevant: `ttl_days` was renamed to `ttl` in v0.90.0 (#28675);
`create_schema` was added in v0.94-ish (#32282); "Exporter now sorts attribute maps' keys
during INSERT, yielding better compression and predictable aggregates" (#33634) — which is
what makes `cityHash64(Attributes)` a stable sort key at all.

**[UNVERIFIED]** I could not find a changelog entry that announces the current metrics
`ORDER BY (ServiceName, MetricName, toStartOfHour(TimeUnix), cityHash64(Attributes),
TimeUnix)`. The entries "Updated the default logs table to a more optimized schema"
(v0.104.0 #33611, v0.107.0 #34203) and "Updated the default trace table" (v0.111.0 #34245)
are all filed under *Enhancements*, not *Breaking changes*, and none of them mention
metrics. So the metrics sort key changed at some point without a breaking-change note. Treat
that as evidence about the process, not just the schema.

**Design consequence.** Do not let an alpha exporter own your production DDL. Set
`create_schema: false`, vendor the DDL from `internal/sqltemplates` into your own migration
repo, and diff it against the upstream templates on every collector bump. The README
endorses exactly this ("for production workloads, it is recommended that you manage your own
schema"). You keep column names/types (the INSERT contract) and own engine, ORDER BY,
PARTITION BY, TTL, and codecs (everything else).

## 2. Idiomatic ClickHouse modelling for OpenLineage events

### 2.0 What you are actually storing

Pinned: OpenLineage tag **`1.53.0`** (released 2026-09-01), spec `$id`
`https://openlineage.io/spec/2-0-2/OpenLineage.json`. Versioning is **SCHEMAVER**
(`MODEL-REVISION-ADDITION`), not semver
([`spec/Versioning.md`](https://github.com/OpenLineage/OpenLineage/blob/1.53.0/spec/Versioning.md)).

The root of the document is a `oneOf` over **three** event shapes:

```json
"oneOf": [
  { "$ref": "#/$defs/RunEvent" },
  { "$ref": "#/$defs/DatasetEvent" },
  { "$ref": "#/$defs/JobEvent" }
]
```

`BaseEvent` requires `eventTime`, `producer`, `schemaURL`. `RunEvent` adds
`eventType ∈ {START, RUNNING, COMPLETE, ABORT, FAIL, OTHER}`, `run{runId (uuid), facets}`,
`job{namespace, name, facets}`, `inputs[]` (`InputDataset`), `outputs[]` (`OutputDataset`);
`run` and `job` are required.

Four structural facts drive the ClickHouse design, and each is a place a naive schema breaks:

1. **`eventType` exists only on `RunEvent`.** `JobEvent` and `DatasetEvent` have none. The
   schema enforces exclusivity: `DatasetEvent` carries `"not": {"required": ["job","run"]}`
   and `JobEvent` carries `"not": {"required": ["run"]}`. So **discriminate on field
   presence, not on `eventType`**, and make `event_type` nullable.
2. **An input dataset has *two* facet maps** — `facets` (`DatasetFacet`) and `inputFacets`
   (`InputDatasetFacet`). `dataQualityMetrics` lives under **`inputFacets`**. There is also a
   near-duplicate `DataQualityMetricsDatasetFacet` (`$id .../1-0-0/`) with byte-identical
   inner properties that hangs under `facets`. **Extraction must check both paths.**
3. **Every facet requires `_producer` and `_schemaURL`** (`BaseFacet`, `additionalProperties:
   true`). Cheap, high-value provenance columns.
4. **Facets replace wholesale.** Per
   [the facets doc](https://openlineage.io/docs/spec/facets/): "Emitting a new facet with the
   same name for the same entity **replaces the previous facet instance for that entity
   entirely**." Last-write-wins per `(entity, facet name)` is therefore the *spec-correct*
   merge semantic — which is exactly `ReplacingMergeTree` ordered by event time.

Facets version **independently** of the core spec (`JobTypeJobFacet` is at MODEL `2` while
most are at `1`). The DQ facets you care about:

| Facet | `$id` version | Attach point | Key |
|---|---|---|---|
| `DataQualityMetricsInputDatasetFacet` | `1-0-3` | `inputs[].inputFacets` | `dataQualityMetrics` |
| `DataQualityMetricsDatasetFacet` | `1-0-0` | `*.facets` | `dataQualityMetrics` |
| `DataQualityAssertionsDatasetFacet` | `1-1-0` | `inputs[].inputFacets` | `dataQualityAssertions` |
| `SchemaDatasetFacet` | `1-2-0` | `*.facets` | `schema` |
| `ColumnLineageDatasetFacet` | `1-2-0` | `*.facets` | `columnLineage` |

`DataQualityMetricsInputDatasetFacet` (required: `columnMetrics`):

```json
"rowCount":    { "type": "integer" },
"bytes":       { "type": "integer" },
"fileCount":   { "type": "integer" },
"lastUpdated": { "type": "string", "format": "date-time" },
"columnMetrics": {
  "description": "The property key is the column name",
  "type": "object",
  "additionalProperties": {
    "type": "object",
    "properties": {
      "nullCount":     { "type": "integer" },
      "distinctCount": { "type": "integer" },
      "sum":           { "type": "number" },
      "count":         { "type": "number" },
      "min":           { "type": "number" },
      "max":           { "type": "number" },
      "quantiles": {
        "description": "The property key is the quantile. Examples: 0.1 0.25 0.5 0.75 1",
        "type": "object",
        "additionalProperties": { "type": "number" }
      }
    }
  }
}
```

Three modelling traps in that snippet. `columnMetrics` is a **map keyed by column name**, not
an array — so flattening to rows requires a map explode, not an `ARRAY JOIN` over a list.
`count` is `"number"` (float) while `nullCount` is `"integer"` — do **not** declare `count` as
`UInt64`. And `quantiles` keys are not normalized in the wild: the OpenLineage repo's own
serde fixture uses `"25"`, contradicting the schema's own `0.25` example, so store them as
`Map(String, Float64)` and normalize downstream.

`DataQualityAssertionsDatasetFacet` at `1-1-0` is much richer than most published examples,
because it grew twice in 2026 (`f7181c7e393c`, 2026-01-16, "add severity"; `b49c04688fe9`,
2026-04-10, PR #4457 adding `name`, `description`, `expected`, `actual`, `content`,
`contentType`, `params`):

```json
"assertions": { "type": "array", "items": {
  "required": ["assertion", "success"],
  "properties": {
    "assertion":   { "type": "string", "example": "not_null" },
    "success":     { "type": "boolean" },
    "column":      { "type": "string", "example": "id" },
    "severity":    { "type": "string", "example": "error" },
    "name":        { "type": "string", "example": "assert_no_orphans" },
    "description": { "type": "string" },
    "expected":    { "type": "string", "example": "1000" },
    "actual":      { "type": "string", "example": "999" },
    "content":     { "type": "string", "example": "SELECT COUNT(*) FROM orders WHERE amount < 0" },
    "contentType": { "type": "string", "example": "sql" },
    "params":      { "type": "object", "additionalProperties": true }
  }
}}
```

`expected` and `actual` are **serialized strings**, not numbers. `success` is deliberately
decoupled from `severity` ("a test can fail without blocking the pipeline when severity is
`warn`") — you need both columns to compute a meaningful failure rate.

**This growth pattern is the whole argument of §2.** Between 1-0-0 and 1-1-0 the assertions
facet gained seven optional fields in four months. Any design that requires a migration per
facet field is the wrong design.

### 2.1 Design (a) — raw JSON column

#### The ClickHouse JSON type is GA. Use it or don't, but know the status.

> "In ClickHouse Open-Source JSON data type is marked as **production ready in version
> 25.3**. It's not recommended to use this type in production in previous versions."
> — [JSON Data Type](https://clickhouse.com/docs/sql-reference/data-types/newjson)

Corroborated from the ClickHouse source: both `allow_experimental_json_type` and
`allow_experimental_object_type` now sit in the `MAKE_OBSOLETE` block of
[`src/Core/Settings.cpp`](https://github.com/ClickHouse/ClickHouse/blob/master/src/Core/Settings.cpp)
(lines 9357, 9433), alongside `use_json_alias_for_old_object_type` (line 9431):

```cpp
MAKE_OBSOLETE(M, Bool, allow_experimental_json_type, true) \
...
MAKE_OBSOLETE(M, Bool, use_json_alias_for_old_object_type, false) \
MAKE_OBSOLETE(M, Bool, describe_extend_object_types, false) \
MAKE_OBSOLETE(M, Bool, allow_experimental_object_type, false) \
```

So: **no `SET allow_experimental_*` is needed for `JSON` on a current server**, and the old
`Object('json')` type's enabling settings are formally obsolete. The old `Object` data-type
doc page now redirects to the new JSON page. (**[UNVERIFIED]:** I could not find a page that
states "`Object('json')` is deprecated" in those words; the evidence is the obsolete-settings
block plus the doc redirect, which is strong but indirect.)

```sql
-- (a-i) Native JSON
CREATE TABLE aiops_dq.ol_event_json
(
    event_time  DateTime64(3)                  CODEC(Delta, ZSTD(1)),
    event       JSON(max_dynamic_paths = 2048) CODEC(ZSTD(3))
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY event_time;

SELECT event.job.name, event.run.runId, event.eventType FROM aiops_dq.ol_event_json;
```

Path access returns `Dynamic`; cast for arithmetic (`event.a.g::Float64`); `event.^a.b`
extracts a sub-object. Skipping indices **do** work on JSON subcolumns, but only on typed
paths or explicitly cast dynamic paths:

```sql
CREATE TABLE sensor_data (
    data JSON(sensor_id UInt32),
    INDEX idx_sensor data.sensor_id TYPE minmax GRANULARITY 1
) ENGINE = MergeTree ORDER BY tuple();
```

Two limits that bite an OpenLineage payload specifically:

- **`max_dynamic_paths` (default 1024).** Exceed it and paths spill into a shared
  `Map(String, String)` structure; the docs warn "reading paths sub-columns from shared data
  may be inefficient as it requires scanning the entire shared data structure". OpenLineage
  events are path-explosive — every `columnMetrics.<colname>.nullCount` is a distinct path,
  so a 200-column dataset generates ~1200 paths *by itself*. **You will blow the default.**
  Monitor with `JSONAllPaths` / `JSONDynamicPaths` / `JSONSharedDataPaths`.
- **JSON subcolumns cannot participate in the primary/sorting key** when lazy type hints are
  in play; the docs note the change "is forbidden" when the affected subcolumn is used in the
  primary/sorting key. So you cannot sort by `event.job.name` — you need an extracted column
  regardless.

```sql
-- (a-ii) String + JSONExtract — the portable, boring option
CREATE TABLE aiops_dq.ol_event_raw
(
    event_time DateTime64(3) CODEC(Delta, ZSTD(1)),
    payload    String        CODEC(ZSTD(3))
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY event_time;

SELECT
    JSONExtractString(payload, 'job', 'name')                        AS job_name,
    JSONExtractString(payload, 'run', 'runId')                       AS run_id,
    JSON_VALUE(payload, '$.inputs[0].inputFacets.dataQualityMetrics.rowCount') AS row_count
FROM aiops_dq.ol_event_raw;
```

`JSONExtract(json, indices_or_keys…, return_type)` can pull a whole typed structure in one
call, e.g. `JSONExtract(payload, 'inputs', 'Array(Tuple(namespace String, name String))')`
([JSON functions](https://clickhouse.com/docs/sql-reference/functions/json-functions)).
The cost is that every read re-parses the entire document — there is no column pruning,
because there is one column.

The mitigation is **`MATERIALIZED` columns**, which are computed at insert and physically
stored ([CREATE TABLE](https://clickhouse.com/docs/sql-reference/statements/create/table)):

```sql
ALTER TABLE aiops_dq.ol_event_raw
    ADD COLUMN IF NOT EXISTS job_name  LowCardinality(String)
        MATERIALIZED JSONExtractString(payload, 'job', 'name'),
    ADD COLUMN IF NOT EXISTS run_id    UUID
        MATERIALIZED toUUIDOrZero(JSONExtractString(payload, 'run', 'runId')),
    ADD INDEX IF NOT EXISTS idx_job job_name TYPE bloom_filter(0.01) GRANULARITY 1;
```

Note two doc'd behaviours: materialized columns are "not included in the result of
`SELECT *`" (toggle with `asterisk_include_materialized_columns`), and the docs do **not**
state whether `ALTER TABLE ADD COLUMN … MATERIALIZED` backfills existing parts —
**[UNVERIFIED]** from primary sources; plan a `ALTER TABLE … MATERIALIZE COLUMN` as part of
the migration rather than assuming.

**Verdict on (a):** best-in-class for **facet schema evolution** — a new field in
`DataQualityAssertionsDatasetFacet` needs zero DDL. Worst for query cost and for anything
that must be a sort key. Correct as an **archive**, wrong as the query surface.

### 2.2 Design (b) — flattened event table

```sql
CREATE TABLE aiops_dq.ol_event_flat
(
    event_time        DateTime64(3)          CODEC(Delta, ZSTD(1)),
    event_type        LowCardinality(String) CODEC(ZSTD(1)),   -- '' for Job/DatasetEvent
    event_kind        Enum8('run'=1,'job'=2,'dataset'=3)  CODEC(ZSTD(1)),
    producer          LowCardinality(String) CODEC(ZSTD(1)),
    schema_url        LowCardinality(String) CODEC(ZSTD(1)),

    job_namespace     LowCardinality(String) CODEC(ZSTD(1)),
    job_name          String                 CODEC(ZSTD(1)),
    run_id            UUID                   CODEC(ZSTD(1)),
    parent_job_name   String                 CODEC(ZSTD(1)),

    -- graph edges, as parallel arrays (one row per event, N datasets)
    input_namespaces  Array(LowCardinality(String)) CODEC(ZSTD(1)),
    input_names       Array(String)                 CODEC(ZSTD(1)),
    output_namespaces Array(LowCardinality(String)) CODEC(ZSTD(1)),
    output_names      Array(String)                 CODEC(ZSTD(1)),

    -- the evolution problem, made concrete:
    dq_row_count      Nullable(UInt64) CODEC(ZSTD(1)),
    dq_bytes          Nullable(UInt64) CODEC(ZSTD(1)),
    assert_names      Array(String)  CODEC(ZSTD(1)),
    assert_success    Array(UInt8)   CODEC(ZSTD(1)),
    assert_severity   Array(LowCardinality(String)) CODEC(ZSTD(1))
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (job_namespace, job_name, event_time);
```

The graph shape `dataset <- run -> job` flattens into this table by keeping `run_id`/`job` as
scalars and the two dataset sides as parallel arrays, then exploding at query time:

```sql
SELECT run_id, job_name, ds_ns, ds_name
FROM aiops_dq.ol_event_flat
ARRAY JOIN input_namespaces AS ds_ns, input_names AS ds_name
WHERE event_type = 'COMPLETE';
```

**Verdict on (b):** fastest to query, and honest about the graph. But every one of the seven
fields added to `DataQualityAssertionsDatasetFacet` in 2026 would have been an `ALTER TABLE`
plus an ingestion change plus a backfill — and old rows would carry `NULL`/`[]` forever, so
"absent because the producer didn't send it" and "absent because the column didn't exist yet"
become indistinguishable. That directly violates the existing convention that
"the absence of a file is meaningful" (`docs/schema-evolution-strategy.md`).
**(b) alone does not survive facet evolution.**

### 2.3 Design (c) — narrow DQ observation table + raw archive ✅

The narrow table stores one row per **(dataset, column, metric, run, time)** measurement.
Facets are a *transport* for measurements; the measurement grain is stable even though the
facet schema is not.

```sql
CREATE TABLE aiops_dq.dq_observation
(
    observed_at       DateTime64(3)          CODEC(Delta, ZSTD(1)),
    dataset_namespace LowCardinality(String) CODEC(ZSTD(1)),   -- 'kafka://kafka:29092'
    dataset_name      LowCardinality(String) CODEC(ZSTD(1)),   -- 'aiops-case-header'
    column_name       LowCardinality(String) CODEC(ZSTD(1)),   -- '' = dataset-level
    metric_name       LowCardinality(String) CODEC(ZSTD(1)),   -- 'nullCount' | 'rowCount' | ...
    value             Float64                CODEC(ZSTD(1)),
    run_id            UUID                   CODEC(ZSTD(1)),
    job_namespace     LowCardinality(String) CODEC(ZSTD(1)),
    job_name          LowCardinality(String) CODEC(ZSTD(1)),
    facet_schema_url  LowCardinality(String) CODEC(ZSTD(1)),   -- provenance, opaque
    facet_producer    LowCardinality(String) CODEC(ZSTD(1)),
    event_id          UUID                   CODEC(ZSTD(1))    -- FK into the raw archive
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(observed_at)
ORDER BY (dataset_namespace, dataset_name, metric_name, column_name, observed_at);
```

Why this survives evolution: the `1-0-0 → 1-1-0` assertions change adds *fields*, not *metric
kinds*. `metric_name` is data, not schema. A new metric is a new **value in a
`LowCardinality(String)` column** — zero DDL, zero backfill, and old rows remain
unambiguously "this metric was not measured then". The 2026 additions land as new rows in the
sibling assertions table below, or as new `metric_name` values.

Assertions want their own narrow table because they are boolean+severity, not numeric:

```sql
CREATE TABLE aiops_dq.dq_assertion
(
    observed_at       DateTime64(3)          CODEC(Delta, ZSTD(1)),
    dataset_namespace LowCardinality(String) CODEC(ZSTD(1)),
    dataset_name      LowCardinality(String) CODEC(ZSTD(1)),
    column_name       LowCardinality(String) CODEC(ZSTD(1)),
    assertion         LowCardinality(String) CODEC(ZSTD(1)),   -- 'not_null' | 'unique' | ...
    assertion_name    String                 CODEC(ZSTD(1)),
    success           UInt8                  CODEC(ZSTD(1)),
    severity          LowCardinality(String) CODEC(ZSTD(1)),   -- 'error' | 'warn' | ''
    expected          String                 CODEC(ZSTD(1)),   -- spec: serialized string
    actual            String                 CODEC(ZSTD(1)),   -- spec: serialized string
    run_id            UUID                   CODEC(ZSTD(1)),
    job_name          LowCardinality(String) CODEC(ZSTD(1)),
    params            String                 CODEC(ZSTD(1)),   -- free-form JSON, verbatim
    event_id          UUID                   CODEC(ZSTD(1))
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(observed_at)
ORDER BY (dataset_namespace, dataset_name, assertion, observed_at);
```

`params` stays a `String` of raw JSON precisely because the spec declares it
`additionalProperties: true` — that is the one place where design (a) is correct *inside*
design (c).

And the archive, which is what makes (c) safe:

```sql
CREATE TABLE aiops_dq.ol_event_raw
(
    event_id     UUID          CODEC(ZSTD(1)),
    event_time   DateTime64(3) CODEC(Delta, ZSTD(1)),
    event_kind   Enum8('run' = 1, 'job' = 2, 'dataset' = 3) CODEC(ZSTD(1)),
    event_type   LowCardinality(String) CODEC(ZSTD(1)),
    job_namespace LowCardinality(String) CODEC(ZSTD(1)),
    job_name      String                CODEC(ZSTD(1)),
    run_id        UUID                  CODEC(ZSTD(1)),
    payload      String        CODEC(ZSTD(3)),
    INDEX idx_job job_name TYPE bloom_filter(0.01) GRANULARITY 1
)
ENGINE = ReplacingMergeTree(event_time)
PARTITION BY toYYYYMM(event_time)
ORDER BY (event_id);
```

`ReplacingMergeTree` matches the spec's own facet semantics (last write wins per entity), but
read the warning:

> "Data deduplication occurs only during a merge. Merging occurs in the background at an
> unknown time, so you can't plan for it." … "it does not guarantee the absence of
> duplicates."
> — [ReplacingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/replacingmergetree)

Use `FINAL` when correctness matters, and remember dedup is **per-partition** — so
`event_id` must not straddle partitions, which it won't since the partition key derives from
`event_time`.

### 2.4 Comparison

| | (a) raw JSON | (b) flattened | (c) narrow + archive |
|---|---|---|---|
| New optional facet field | free | `ALTER` + backfill | free |
| New metric kind | free | `ALTER` | free (new `metric_name` value) |
| New facet entirely | free | new table | free (archive) + optional new extractor |
| Sort-key pruning on dataset | ✗ (JSON subcols can't be in the key) | ✓ | ✓ |
| Query cost, single metric over 90d | full doc parse per row | column read | column read, sort-key pruned |
| Distinguishes "not measured" from "field didn't exist" | ✓ | ✗ | ✓ |
| Grafana-friendly | ✗ | ✓ | ✓ |
| Replay/audit fidelity | ✓ (byte-exact) | ✗ (lossy) | ✓ (archive is byte-exact) |

**Recommendation: (c).** The narrow table is the query surface and carries a long TTL; the
raw archive is the audit surface and carries an even longer one, mirroring the existing
"immutable, hash-chained, write-once" casefile posture in
`docs/schema-evolution-strategy.md`. Design (b) is a trap that looks like the fastest option
until the fourth facet revision. Design (a) alone is an archive pretending to be a database.

**Migration property worth stating explicitly:** because the archive is byte-exact, a *new*
extractor for a *newly interesting* facet field can be backfilled over history without
re-ingesting from Kafka. That is the single strongest argument for keeping the raw payload,
and it is the same argument the repo already makes for keeping stage files immutable.

## 3. The join: metric series × DQ observation series in one query

### 3.1 What the two tables must share

A join is not free. Three things have to be made true *by design*, not discovered at query
time:

| Requirement | Metric side | DQ side | Bridge |
|---|---|---|---|
| **Time** | `TimeUnix DateTime` (second precision) | `observed_at DateTime64(3)` | bucket both with `toStartOfInterval(…, INTERVAL 5 MINUTE)`; never join raw timestamps |
| **Entity** | `ServiceName` + `Attributes['messaging.destination.name']` | `dataset_namespace` + `dataset_name` | an explicit mapping table / dictionary |
| **Ordering** | sorted by `(ServiceName, MetricName, …, TimeUnix)` | sorted by `(ns, name, metric, col, observed_at)` | ASOF requires an ordered numeric/date key on both sides |

**Time granularity.** The exporter stores `TimeUnix` as `DateTime` — **whole seconds**. The
OL `eventTime` is `format: date-time` with sub-second precision. Joining `DateTime` to
`DateTime64(3)` works but silently promotes; worse, "same instant" is meaningless across two
independently-clocked producers. Pick one grid (5 minutes is a defensible default given the
15s Prometheus scrape interval in `config/prometheus.yml`) and bucket both sides.

**Entity keys — this is the hard part.** OpenLineage identity is the **pair**
`(namespace, name)`; there is no single URI field. Per the
[naming conventions](https://openlineage.io/docs/spec/naming):

| Store | Namespace | Name |
|---|---|---|
| Kafka | `kafka://{bootstrap server host}:{port}` | `{topic}` |
| Postgres | `postgres://{host}:{port}` | `{database}.{schema}.{table}` |

So for this repo, `aiops-case-header` as an OL dataset is
`("kafka://kafka:29092", "aiops-case-header")`, and the outbox table is
`("postgres://postgres:5432", "aiops.public.outbox")`.

On the OTel side, the corresponding identity lives in `ResourceAttributes` /`Attributes` under
the messaging semantic conventions (`messaging.system`, `messaging.destination.name`,
`server.address`, `server.port`). Two warnings:

1. **The bootstrap host in the OL namespace is whatever *one* bootstrap server that producer
   was configured with.** It is not a cluster identity and is not guaranteed stable across
   producers pointing at the same cluster. The spec offers no cluster-identity concept;
   `SymlinksDatasetFacet` is the blessed escape hatch for alternate names.
2. `Attributes['k']` on a missing key returns `''`, not `NULL`. Every bridge predicate needs
   an explicit non-empty guard or you will silently join everything to everything.

**Therefore: do not join on parsed strings. Materialise the bridge.** A small, hand-curated,
version-controlled dimension table is the only honest answer, and it is the artifact the
architecture review should actually scrutinise:

```sql
CREATE TABLE aiops_dq.entity_map
(
    dataset_namespace LowCardinality(String),
    dataset_name      LowCardinality(String),
    service_name      LowCardinality(String),   -- OTel ServiceName
    attr_key          LowCardinality(String),   -- e.g. 'messaging.destination.name'
    attr_value        String,                   -- e.g. 'aiops-case-header'
    valid_from        DateTime DEFAULT toDateTime(0),
    note              String DEFAULT ''
)
ENGINE = ReplacingMergeTree(valid_from)
ORDER BY (dataset_namespace, dataset_name, service_name, attr_key);

INSERT INTO aiops_dq.entity_map
    (dataset_namespace, dataset_name, service_name, attr_key, attr_value, note) VALUES

```

([Dictionaries](https://clickhouse.com/docs/sql-reference/dictionaries)) so lookups are

### 3.2 Time-bucket join — the one to reach for first

Explicit, debuggable, and it works with Grafana's `$__timeFilter`/`$__timeInterval` macros
without contortion.

```sql
-- "Did a DQ anomaly on aiops-case-header coincide with a Kafka lag spike?"
WITH
    toStartOfInterval(now() - INTERVAL 24 HOUR, INTERVAL 5 MINUTE) AS t_from,
    now() AS t_to,

    lag AS (
        SELECT
            toStartOfInterval(TimeUnix, INTERVAL 5 MINUTE)      AS bucket,
            ServiceName                                          AS service_name,
            Attributes['messaging.destination.name']             AS topic,
            max(Value)                                           AS lag_max
        FROM otel.otel_metrics_gauge
        WHERE MetricName = 'kafka_consumergroup_lag'
          AND TimeUnix >= t_from AND TimeUnix < t_to
          AND Attributes['messaging.destination.name'] != ''     -- Map default is '', not NULL
        GROUP BY bucket, service_name, topic
    ),

    dq AS (
        SELECT
            toStartOfInterval(o.observed_at, INTERVAL 5 MINUTE)  AS bucket,
            m.service_name                                        AS service_name,
            m.attr_value                                          AS topic,
            o.dataset_name                                        AS dataset_name,
            o.column_name                                         AS column_name,
            o.metric_name                                         AS metric_name,
            avg(o.value)                                          AS dq_value,
            count()                                               AS dq_n
        FROM aiops_dq.dq_observation AS o
        INNER JOIN aiops_dq.entity_map AS m
               ON  m.dataset_namespace = o.dataset_namespace
               AND m.dataset_name      = o.dataset_name
        WHERE o.observed_at >= t_from AND o.observed_at < t_to
          AND m.attr_key = 'messaging.destination.name'
        GROUP BY bucket, service_name, topic, dataset_name, column_name, metric_name
    )

SELECT
    coalesce(lag.bucket, dq.bucket)   AS bucket,
    coalesce(lag.topic,  dq.topic)    AS topic,
    lag.lag_max,
    dq.dataset_name, dq.column_name, dq.metric_name, dq.dq_value, dq.dq_n
FROM lag
FULL OUTER JOIN dq
     ON lag.bucket = dq.bucket AND lag.topic = dq.topic
ORDER BY bucket, topic
SETTINGS join_use_nulls = 1;
```

`FULL OUTER JOIN` is deliberate: "the lag spiked and there was **no** DQ observation" is as
much an answer as a coincidence, and an inner join hides it. `join_use_nulls = 1` makes the
non-matching side `NULL` rather than type defaults — without it a missing `lag_max` reads as
`0`, which is a lie.

### 3.3 ASOF join — when you want "the metric value nearest each DQ event"

Better shape when DQ events are genuinely sparse: don't grid them, just attach the nearest
preceding metric sample to each one.

> "The `asof_column` column is always the last one in the `USING` clause." … the closest-match
> column "must contain an ordered sequence" and be Int/UInt/Float/Date/DateTime/Decimal.
> Supported operators for the closest-match condition: `>`, `>=`, `<`, `<=`. "ASOF JOIN is
> supported only by `hash` and `full_sorting_merge` join algorithms. It's **not** supported in
> the `Join` table engine."
> — [JOIN clause](https://clickhouse.com/docs/sql-reference/statements/select/join)

```sql
SELECT
    o.observed_at,
    o.dataset_name,
    o.column_name,
    o.metric_name,
    o.value                                AS dq_value,
    g.TimeUnix                             AS metric_at,
    g.Value                                AS lag_at_that_moment,
    dateDiff('second', g.TimeUnix, o.observed_at) AS skew_s
FROM aiops_dq.dq_observation AS o
INNER JOIN aiops_dq.entity_map AS m
        ON m.dataset_namespace = o.dataset_namespace
       AND m.dataset_name      = o.dataset_name
       AND m.attr_key          = 'messaging.destination.name'
ASOF LEFT JOIN
(
    SELECT
        Attributes['messaging.destination.name'] AS topic,
        TimeUnix,
        Value
    FROM otel.otel_metrics_gauge
    WHERE MetricName = 'kafka_consumergroup_lag'
      AND TimeUnix >= now() - INTERVAL 7 DAY
      AND Attributes['messaging.destination.name'] != ''
) AS g
    ON  g.topic     =  m.attr_value               -- equi conditions first
    AND g.TimeUnix  <= o.observed_at              -- closest-match condition LAST
WHERE o.observed_at >= now() - INTERVAL 7 DAY
  AND o.metric_name = 'nullCount'
ORDER BY o.observed_at DESC
LIMIT 500;
```

Three things to get right, all of which are ways this query silently misleads:

1. **The inequality must be the last `ON` condition**, and it must point the right way.
   `g.TimeUnix <= o.observed_at` gives the last metric sample *at or before* the DQ
   observation — causally correct. Flip it and you are attributing a lag spike to a DQ event
   that happened after it.
2. **`ASOF LEFT JOIN`, not `ASOF JOIN`.** Inner drops DQ observations with no preceding metric
   sample — which is exactly the "the collector was down" case you most want to see.
3. **`skew_s` is not decoration.** ASOF will happily match a DQ event to a metric sample from
   six hours earlier if that is the nearest one. Always project the gap and filter
   (`WHERE skew_s < 900`) or you will manufacture correlations. ClickHouse has no
   `ASOF … WITHIN INTERVAL` tolerance clause — **[UNVERIFIED]** that any such clause exists;
   I found none in the JOIN docs, so post-filtering is the mechanism.

### 3.4 Which to use

| Situation | Use |
|---|---|
| Dashboard panel, both series on a shared grid, want gaps visible | **time-bucket `FULL OUTER JOIN`** (§3.2) |
| "For each DQ event, what was the metric doing?" | **`ASOF LEFT JOIN`** (§3.3) |
| Grafana overlay of DQ events on an existing metric panel | **no join at all** — an annotation query (§7.5) |

The third row is worth dwelling on. Half the "did these coincide?" questions are answered
better by rendering the DQ event as a Grafana **region annotation** over the existing metric
panel than by a join. That costs no join key alignment at all and is the cheapest first
increment of this whole proposal.

## 4. Baseline computation over dense and sparse series

"Baseline" here means the same thing it means in `pipeline/stages/baseline_deviation.py`:
a per-entity, per-bucket expected value and spread, against which a live observation is
scored. In ClickHouse there are three idioms, and which one is correct depends entirely on
whether the series is dense or sparse.

### 4.1 Dense metric table — window functions

Window functions are the natural fit when every bucket has a row. Syntax:

```sql
aggregate_function (column_name)
  OVER ([[PARTITION BY grouping_column] [ORDER BY sorting_column]
        [ROWS, RANGE, or GROUPS expression_to_bound_rows_within_the_group]]
        | [window_name])
```

— [Window Functions](https://clickhouse.com/docs/sql-reference/window-functions)

The default frame, when `ORDER BY` is present and no frame is given, is
`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` — i.e. cumulative, not rolling. If you
want a rolling baseline you must state the frame.

**The single most important gotcha for a time-series baseline:** ClickHouse **does not
support `RANGE BETWEEN INTERVAL '1' DAY PRECEDING`**. The docs say to "specify the number of
seconds instead (`RANGE` works with any numeric type)"
([Window Functions](https://clickhouse.com/docs/sql-reference/window-functions)). So a
time-based `RANGE` frame requires ordering by a **numeric** time expression, not a
`DateTime`. In practice: bucket to a fixed grid, convert to a number, and order by that.

A 6-hour trailing mean/stddev baseline over the exporter's sum table, on a 5-minute grid:

```sql
WITH bucketed AS (
    SELECT
        ServiceName,
        MetricName,
        Attributes['topic']                                   AS topic,
        toStartOfInterval(TimeUnix, INTERVAL 5 MINUTE)        AS bucket,
        max(Value)                                            AS v      -- cumulative counter
    FROM otel.otel_metrics_sum
    WHERE MetricName = 'kafka_consumergroup_lag'
      AND TimeUnix >= now() - INTERVAL 7 DAY
    GROUP BY ServiceName, MetricName, topic, bucket
)
SELECT
    ServiceName,
    topic,
    bucket,
    v,
    avg(v)   OVER w AS baseline_mean,
    stddevPop(v) OVER w AS baseline_sd,
    (v - avg(v) OVER w) / nullIf(stddevPop(v) OVER w, 0) AS z
FROM bucketed
WINDOW w AS (
    PARTITION BY ServiceName, topic
    ORDER BY toUInt32(bucket)                 -- numeric ordering: RANGE needs this
    RANGE BETWEEN 21600 PRECEDING AND 1 PRECEDING   -- 6h trailing, excludes current bucket
)
ORDER BY ServiceName, topic, bucket;
```

`toUInt32(bucket)` yields Unix seconds, so `21600 PRECEDING` is literally "6 hours". Excluding
the current row (`AND 1 PRECEDING`) keeps the observation out of its own baseline — otherwise
a large spike inflates its own expected value and suppresses its z-score.

`ROWS BETWEEN n PRECEDING AND CURRENT ROW` is the cheaper alternative and is correct **only
if the grid is guaranteed dense**, because `ROWS` counts rows, not time. On a dense metric
table after `GROUP BY bucket` it is dense *only where data existed*: a collector outage
produces no rows at all, and `ROWS BETWEEN 72 PRECEDING` will silently reach back across the
gap into much older data. `RANGE` on a numeric time column does not have this bug. Prefer
`RANGE`.

Seasonal (hour-of-week) baselines — the shape the peak/baseline-deviation stages actually
use — are a plain `GROUP BY`, not a window:

```sql
SELECT
    Attributes['topic']                              AS topic,
    toDayOfWeek(TimeUnix)                            AS dow,
    toHour(TimeUnix)                                 AS hod,
    quantilesTDigest(0.5, 0.9, 0.99)(Value)          AS p50_p90_p99,
    count()                                          AS n
FROM otel.otel_metrics_gauge
WHERE MetricName = 'aiops_findings_rate'
  AND TimeUnix >= now() - INTERVAL 28 DAY
GROUP BY topic, dow, hod
HAVING n >= 200;                                     -- refuse to publish thin baselines
```

### 4.2 Quantiles: which function, and why it matters here

| Function | Semantics | Cost | Determinism |
|---|---|---|---|
| `quantileTDigest(level)(expr)` | approximate, t-digest | memory `log(n)`; "lower performance than `quantile`/`quantileTiming`" but "superior state-size-to-precision ratio" | **"The result depends on the order of running the query, and is nondeterministic."** |
| `quantileExactWeighted(level)(expr, weight)` | **exact**, weight = "number of value occurrences" (UInt*) | hash table keyed on value; cheap when values repeat, expensive when they don't | deterministic |
| `quantiles*(l1, l2, …)(expr)` | plural family, all levels in one pass, returns `Array` | one pass | as per base function |

Sources: [quantileTDigest](https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/quantiletdigest),
[quantileExactWeighted](https://clickhouse.com/docs/sql-reference/aggregate-functions/reference/quantileexactweighted).

**The nondeterminism note on `quantileTDigest` is not academic for this system.** The
schema-evolution doc's audit story ("an auditor replaying this decision needs … the policy
versions to reproduce the gating decision") assumes a decision is reproducible. If a gate
threshold is a `quantileTDigest` computed at query time, replaying the query can produce a
different number. Two mitigations, both defensible:

1. Compute the baseline **once**, materialise it into a table with a `baseline_version`, and
   have the gate read the materialised row — never recompute at decision time.
2. Where the value domain is small and repetitive (bucketed lag values, row counts),
   use `quantilesExactWeighted` and get determinism for free:

```sql
SELECT
    dataset_name,
    column_name,
    quantilesExactWeighted(0.5, 0.95, 0.99)(toUInt64(value), 1) AS q
FROM aiops_dq.dq_observation
WHERE metric_name = 'null_ratio_bp'          -- integer basis points, deliberately
  AND observed_at >= now() - INTERVAL 90 DAY
GROUP BY dataset_name, column_name;
```

### 4.3 Sparse observation table — what actually breaks

Applying §4.1 to a sparse DQ table breaks in four specific ways.

1. **Empty buckets do not exist.** `GROUP BY toStartOfInterval(observed_at, INTERVAL 1 HOUR)`
   emits no row for an hour with no observation. A rolling mean over "the last 24 buckets"
   is then a rolling mean over "the last 24 *observations*", which may span three weeks.
   Fix with `WITH FILL`:

```sql
SELECT
    toStartOfInterval(observed_at, INTERVAL 1 DAY) AS d,
    avgOrNull(value)                                AS v
FROM aiops_dq.dq_observation
WHERE dataset_name = 'aiops-case-header' AND metric_name = 'null_ratio_bp'
  AND observed_at >= now() - INTERVAL 90 DAY
GROUP BY d
ORDER BY d
    WITH FILL FROM toStartOfDay(now() - INTERVAL 90 DAY)
              TO   toStartOfDay(now())
              STEP INTERVAL 1 DAY
    INTERPOLATE (v AS v);      -- carry last value forward; omit to leave 0/NULL
```

   Syntax and semantics: `ORDER BY expr WITH FILL [FROM x] [TO y] [STEP z] [STALENESS s]
   [INTERPOLATE (col AS expr, …)]`
   ([ORDER BY / WITH FILL](https://clickhouse.com/docs/sql-reference/statements/select/order-by)).
   `STALENESS` is the important one for sparse data: it "limits filling — row generation
   stops when the difference from the previous original row exceeds this threshold", which
   is how you avoid interpolating a flat line across a two-month gap and calling it a
   baseline. `FROM`/`TO` bounds appear inclusive.

   Note the ordering: `WITH FILL` is part of `ORDER BY`, so it runs **after** aggregation and
   **after** window functions in the same SELECT. You cannot window over filled rows in one
   statement — you need the filled result as a subquery/CTE and a window in the outer query.

2. **`RANGE` frames need time-ordered numeric ordering.** Same constraint as §4.1, but it
   bites harder: with sparse data you cannot substitute `ROWS` as a shortcut, because row
   count and elapsed time are completely decoupled. `RANGE BETWEEN 2592000 PRECEDING AND 1
   PRECEDING` over `toUInt32(bucket)` is the only correct form.

3. **Insufficient sample counts.** A z-score over three observations is noise. Always carry
   `count()` alongside and gate on it:

```sql
SELECT
    dataset_name, column_name, metric_name, bucket, value,
    avg(value)      OVER w AS mu,
    stddevPop(value) OVER w AS sd,
    count()         OVER w AS n,
    if(n >= 30, (value - mu) / nullIf(sd, 0), NULL) AS z   -- NULL, not a fake score
FROM (
    SELECT dataset_name, column_name, metric_name,
           toStartOfInterval(observed_at, INTERVAL 1 HOUR) AS bucket,
           avg(value) AS value
    FROM aiops_dq.dq_observation
    WHERE observed_at >= now() - INTERVAL 90 DAY
    GROUP BY dataset_name, column_name, metric_name, bucket
)
WINDOW w AS (
    PARTITION BY dataset_name, column_name, metric_name
    ORDER BY toUInt32(bucket)
    RANGE BETWEEN 2592000 PRECEDING AND 1 PRECEDING     -- 30 days
);
```

   Emitting `NULL` rather than a computed z when `n < 30` is the whole point: a downstream
   finding must be able to distinguish "not anomalous" from "not enough evidence". This maps
   directly onto the existing convention that "the absence of a file is meaningful"
   (`docs/schema-evolution-strategy.md`).

4. **`stddevPop` vs `stddevSamp`.** With small `n` these differ materially. Pick one and
   record it in the baseline artifact's version, or two replays disagree.

### 4.4 Where materialized views fit — and where they don't

`AggregatingMergeTree` "replaces rows sharing the same sorting key with a single row (within
a single data part) that stores a combination of states of aggregate functions"
([AggregatingMergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/aggregatingmergetree)).
Combined with an MV you get incremental, insert-time aggregation:

```sql
CREATE MATERIALIZED VIEW test.visits_mv TO test.agg_visits
AS SELECT StartDate, CounterID, sumState(Sign) AS Visits, uniqState(UserID) AS Users
FROM test.visits GROUP BY StartDate, CounterID;

SELECT StartDate, sumMerge(Visits) AS Visits, uniqMerge(Users) AS Users
FROM test.visits_mv GROUP BY StartDate;
```

`-State` "does not return the resulting value … but an intermediate state of the
aggregation", typed `AggregateFunction(...)`; `-Merge` "takes the intermediate aggregation
state as an argument, combines the states to finish aggregation, and returns the resulting
value"
([Combinators](https://clickhouse.com/docs/sql-reference/aggregate-functions/combinators)).

**MVs are the right tool for the dense side.** A 5-minute rollup of the sum table pays the
aggregation cost once at insert and turns every dashboard/baseline query into a scan of a
table ~60× smaller. See [Proposed design](#proposed-design) for the DDL.

**MVs are a poor tool for the sparse side, and it is worth being blunt about why.** Four
concrete failure modes:

- **An MV is an insert trigger, not a view.** It fires on blocks inserted into the source
  table. Historical rows are not reprocessed (absent `POPULATE`, which is itself racy
  against concurrent inserts). Backfilling a DQ baseline after a facet change means
  rebuilding by hand.
- **An MV cannot see across the join.** The MV's `SELECT` runs against the inserted block
  only. You cannot write an MV that joins the DQ event to the metric series and materialises
  a correlation, because the metric rows are not in the block. Cross-signal correlation is a
  **query-time** operation (see [§3](#3-the-join-metric-series--dq-observation-series-in-one-query)),
  or a scheduled job writing to a third table — not an MV.
- **Sparse data does not amortise.** The value of an AggregatingMergeTree MV is turning
  billions of rows into thousands. Thousands of DQ observations per day are already
  thousands. There is no win, and you've added a schema-coupled object that has to be
  dropped and recreated on every column change.
- **`-State` columns are a versioning liability.** `AggregateFunction(quantileTDigest, …)`
  states are an internal binary format tied to the function; changing the function or its
  parameters means the stored states are no longer mergeable with new ones. For a system
  whose whole point is auditable replay 20 months later, that is a real risk. Dense
  metrics can afford it (short TTL, regenerable). A 2-year DQ baseline cannot.

**Rule of thumb for this design:** MV + AggregatingMergeTree on the dense metric path with
a short TTL; plain `MergeTree` plus scheduled/query-time aggregation on the sparse DQ path,
with baselines materialised as *ordinary numeric rows* carrying a `baseline_version`, not as
aggregate states.

## 5. Sparse vs dense in one system

### 5.1 They are genuinely different workloads

| | Dense metrics | Sparse DQ observations |
|---|---|---|
| Rows/day (order of magnitude) | 10⁶–10⁹ | 10³–10⁵ |
| Arrival | regular, machine-paced (15s scrape) | irregular, event-paced (per pipeline run) |
| Read pattern | narrow time window, many series | wide time window, few series |
| Value of an individual row | ~zero (interchangeable with neighbours) | high (each is an audited fact) |
| Correct retention | days–weeks raw, months rolled up | years, raw |
| Regenerable? | yes, mostly | **no** |
| Cardinality driver | label combinations | dataset × column × metric |

The last two rows are the ones that force different treatment. A dropped metric sample is
noise; a dropped DQ observation is a hole in an audit trail.

### 5.2 Engine

**Same family, different members — and that is fine.**

- Metrics raw: `MergeTree`. This is what the exporter emits and there is no reason to change
  it. `ReplacingMergeTree` would be wrong (there is no natural dedup key; `cityHash64` is a
  hash, not an identity), and `SummingMergeTree` would be wrong (it collapses distinct series
  that hash-collide, and you lose min/max).
- Metrics rollup: `AggregatingMergeTree` fed by an MV — the case for `-State` columns is
  strongest exactly where the data is regenerable and short-lived (see [§4.4](#44-where-materialized-views-fit--and-where-they-dont)).
- DQ observations: **plain `MergeTree`**. Volume does not justify an aggregating engine, and
  `-State` columns are a versioning liability on a multi-year retention (§4.4).
- DQ raw archive: `ReplacingMergeTree(event_time)` — because the *spec itself* defines
  last-write-wins-per-entity facet semantics (§2.0, point 4). This is the one place where the
  engine choice is derived from the data model rather than from performance.

### 5.3 ORDER BY

This is where the two shapes genuinely diverge, and the divergence is principled:

```sql
-- metrics: time-first-ish, attributes as an opaque hash
ORDER BY (ServiceName, MetricName, toStartOfHour(TimeUnix), cityHash64(Attributes), TimeUnix)

-- DQ: entity-first, time last
ORDER BY (dataset_namespace, dataset_name, metric_name, column_name, observed_at)
```

The metric key puts a coarse time bucket **third** because the dominant query is "this metric,
this service, last N hours" — a narrow time slice across many series. The DQ key puts time
**last** because the dominant query is "this dataset's null ratio, last 90 days" — a wide time
slice across one series. Putting `observed_at` early in the DQ key would destroy locality for
exactly the query the table exists to serve.

The metric key's `cityHash64(Attributes)` is only stable because the exporter "sorts attribute
maps' keys during INSERT, yielding better compression and predictable aggregates" (#33634).
Note what this buys and what it doesn't: you can prune on an *exact whole-map* match, not on a
single label. Single-label filtering falls to the bloom filters, with the caveat the exporter
README itself spells out (§1.2). **If topic-level filtering is on the hot path, hoist the
topic out of the map into a real column in your own DDL** — see the Proposed design.

### 5.4 PARTITION BY

```sql
-- metrics
PARTITION BY toDate(TimeUnix)      -- daily; the exporter's default
-- DQ
PARTITION BY toYYYYMM(observed_at) -- monthly
```

Daily partitions on metrics exist to make `ttl_only_drop_parts = 1` cheap: a whole day expires
as a metadata operation. Daily partitions on a table producing a few thousand rows/day would
be pathological — thousands of tiny parts, each with its own overhead, and the docs' own
guidance is that "generally you do not need a partition key more granular than by month"
([MergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree)).
Monthly on the DQ side; 24-month retention is then 24 partitions.

### 5.5 TTL

Fully divergent — see [§8](#8-retention). Metrics: 14d raw → 180d 5-minute rollup → drop. DQ:
730d raw, no rollup, because the row *is* the record.

### 5.6 So is this "one storage system", or two tables sharing a server?

**Be honest: co-location alone is marketing.** Two tables in the same server share a process
and a backup schedule. That is an ops convenience, not an architecture.

What actually makes it one system — the four things a review should demand evidence of:

1. **A shared, materialised join key.** `entity_map` (§3.1). Without a curated, owned,
   version-controlled bridge from `(dataset_namespace, dataset_name)` to
   `(ServiceName, attr_key, attr_value)`, cross-signal queries are string-munging that breaks
   the first time a broker is renamed. **This artifact is the integration.** If it does not
   exist and have an owner, the claim of "one system" is false.
2. **A shared time grid.** A documented, enforced bucket (5 minutes) that both sides round to,
   so `toStartOfInterval` on either table produces joinable keys. Otherwise every join is
   bespoke and every analyst picks a different bucket.
3. **A single query engine that can express the join.** This is the real, non-marketing win,
   and it is genuinely large: `ASOF LEFT JOIN` across a metric series and an event series is
   **not expressible in PromQL at all**, at any price. That is the actual reason to do this.
4. **Cross-table objects that only work because of co-location.** A dictionary over
   `entity_map` used from a metric query; a scheduled job writing correlation scores from both
   tables into a third. Note what is *not* on this list: **a materialized view cannot span the
   two tables**, because an MV fires on an inserted block and cannot see rows in another table
   (§4.4). Anyone promising "an MV that correlates metrics with DQ events" is wrong.

**Where the "one system" claim is weakest.** Retention is fully divergent, engines differ,
sort keys differ, partition granularity differs, and Grafana's ClickHouse datasource models
the DQ side well and the metrics side not at all (§7.6). A reviewer is entitled to ask: if the
two halves share nothing but a hostname and a join key you had to hand-curate anyway, why not
leave metrics in Prometheus? That question has a real answer — the join in point 3 — but only
if someone is actually going to write those queries. **If the only artifact anyone ever builds
is a Grafana annotation overlay, the honest recommendation is to skip the metrics migration
entirely** (see Proposed design, Phase 1).

### 6.3 Kafka transport — config keys differ between Java and Python

|---|---|---|
| topic key | **`topicName`** | **`topic`** |
| producer props | **`properties`** | **`config`** |
| message key | `messageKey` | `messageKey` (alias `message_key`) |

### 6.4 Wire format — the answer that unlocks the ClickHouse Kafka engine

From `KafkaTransport.java` @ 1.53.0:

```java
@Override
public void emit(@NonNull OpenLineage.RunEvent runEvent) {
  emit(OpenLineageClientUtils.toJson(runEvent), getMessageKey(runEvent));
}

private void emit(String eventAsJson, String eventKey, Duration timeout) {
  String partitionKey = messageKey;
  if (partitionKey == null) { partitionKey = eventKey; }
  final ProducerRecord<String, String> record =
      new ProducerRecord<>(topicName, partitionKey, eventAsJson);
  ...
}
```

| Question | Answer |
|---|---|
| One event per message? | **Yes** — one `ProducerRecord` per `emit()`. No OL-layer batching. |
| JSON object or NDJSON? | **A single JSON object per message.** No trailing newline, no envelope, no wrapper. The value is exactly `toJson(event)`. |
| Value/key type | `ProducerRecord<String, String>` (hence `StringSerializer` in every doc example); UTF-8 bytes in Python. |
| Schema registry / Avro / Protobuf? | **No.** Plain JSON, no magic byte, no registry wire format. |
| Record headers / compression | None set by OL — the 3-arg `ProducerRecord` ctor adds no headers. Compression only via raw `compression.type`. |

**That is precisely `JSONAsString` (or `JSONEachRow`) for the ClickHouse Kafka engine.**

**Message key semantics**, verbatim from the source comment:

```java
/*
  To keep order of events in Kafka topic, we need to send them to the same partition.
  For (1) Kafka messageKey has format "run:<namespace>/<name>".
  For (2) source for `<namespace>` and `<name>` is selected using this order:
  - run.facets.parent.root.job
  - run.facets.parent.job
  - run.job
*/
```

Resolution order (identical in Java and Python): explicit `messageKey` config wins; else
RunEvent → `run:{root.job.ns}/{root.job.name}` → `run:{parent.job…}` → `run:{job…}`;
JobEvent → `job:{ns}/{name}`; DatasetEvent → `dataset:{ns}/{name}`.

⚠️ **The Java transport doc contains a stale, wrong copy of these defaults.** The
`#### Configuration` block in `website/docs/client/java/partials/java_transport.md` is
correct; the trailing `*Notes*` block claims `run:{job.namespace}/{job.name}/{run.id}`.
**There is no run id in the key.** The source proves it. If you sized partitions assuming
run-id in the key you would get wildly different cardinality. Trust the code.

Consequences you can rely on: **per-job ordering is guaranteed** (START before COMPLETE for a
given job, including across a parent→child hierarchy when the parent facets are set); there is
**no ordering across jobs**; and because the key is per-*job* not per-*run*, **a hot job is a
hot partition**.

```sql
(
    payload String

SETTINGS

    kafka_thread_per_consumer = 1,
    kafka_handle_error_mode  = 'stream',         -- surface bad messages instead of throwing
    kafka_skip_broken_messages = 0;

-- 2. Landing MV -> the raw archive (see 2.3 for the target DDL).
CREATE MATERIALIZED VIEW aiops_dq.mv_ol_event_raw TO aiops_dq.ol_event_raw AS
SELECT
    generateUUIDv4()                                                  AS event_id,
    parseDateTime64BestEffortOrZero(JSONExtractString(payload, 'eventTime'), 3) AS event_time,
    multiIf(JSONHas(payload, 'run'),     'run',
            JSONHas(payload, 'dataset'), 'dataset',
                                         'job')                       AS event_kind,
    JSONExtractString(payload, 'eventType')                           AS event_type,
    JSONExtractString(payload, 'job', 'namespace')                    AS job_namespace,
    JSONExtractString(payload, 'job', 'name')                         AS job_name,
    toUUIDOrZero(JSONExtractString(payload, 'run', 'runId'))          AS run_id,
    payload
FROM aiops_dq.ol_event_queue
WHERE _error = '';        -- kafka_handle_error_mode='stream' virtual column

-- 2b. Dead-letter: keep unparseable messages instead of losing them.
CREATE TABLE aiops_dq.ol_event_dlq
(
    seen_at DateTime DEFAULT now(),
    topic   LowCardinality(String),
    partition_id UInt64,
    offset_id    UInt64,
    error   String,
    raw     String
) ENGINE = MergeTree ORDER BY seen_at TTL seen_at + INTERVAL 30 DAY;

CREATE MATERIALIZED VIEW aiops_dq.mv_ol_event_dlq TO aiops_dq.ol_event_dlq AS
SELECT now() AS seen_at, _topic AS topic, _partition AS partition_id,
       _offset AS offset_id, _error AS error, _raw_message AS raw
FROM aiops_dq.ol_event_queue
WHERE _error != '';

-- 3. Fan-out MV: explode columnMetrics maps into narrow observations.
CREATE MATERIALIZED VIEW aiops_dq.mv_dq_observation TO aiops_dq.dq_observation AS
WITH
    parseDateTime64BestEffortOrZero(JSONExtractString(payload, 'eventTime'), 3) AS ts,
    toUUIDOrZero(JSONExtractString(payload, 'run', 'runId'))                    AS rid,
    JSONExtractArrayRaw(payload, 'inputs')                                      AS inputs
SELECT
    ts                                                            AS observed_at,
    JSONExtractString(inp, 'namespace')                           AS dataset_namespace,
    JSONExtractString(inp, 'name')                                AS dataset_name,
    col_kv.1                                                      AS column_name,
    metric_kv.1                                                   AS metric_name,
    metric_kv.2                                                   AS value,
    rid                                                           AS run_id,
    JSONExtractString(payload, 'job', 'namespace')                AS job_namespace,
    JSONExtractString(payload, 'job', 'name')                     AS job_name,
    JSONExtractString(dqm, '_schemaURL')                          AS facet_schema_url,
    JSONExtractString(dqm, '_producer')                           AS facet_producer,
    generateUUIDv4()                                              AS event_id
FROM aiops_dq.ol_event_queue
ARRAY JOIN inputs AS inp
-- NOTE: check BOTH facet maps (see 2.0, point 2)
ARRAY JOIN [ JSONExtractRaw(inp, 'inputFacets', 'dataQualityMetrics'),
             JSONExtractRaw(inp, 'facets',      'dataQualityMetrics') ] AS dqm
ARRAY JOIN JSONExtractKeysAndValuesRaw(dqm, 'columnMetrics')       AS col_kv
ARRAY JOIN JSONExtractKeysAndValues(col_kv.2, 'Float64')           AS metric_kv
WHERE _error = '' AND dqm != '' AND metric_kv.1 != 'quantiles';
```

Two caveats on that last MV, stated plainly rather than hidden:

- **It is illustrative, not tested.** The chained `ARRAY JOIN` over `JSONExtract*Raw` is the
  right *shape*, but the exact function/argument spellings need to be validated against your
  server version before anyone pastes it into a migration. **[UNVERIFIED]** as executable SQL.
- `quantiles` is excluded because it is a nested map of maps and does not flatten in the same
  pass; it needs a second MV writing `metric_name = concat('q', quantile_key)`.

**Reliability posture.** The Kafka engine is **at-least-once**: offsets are committed after
data reaches target tables via MVs, and the docs advise `fsync_after_insert = 1` on MergeTree
targets since page-cache loss can silently drop rows despite a committed offset
([Kafka engine](https://clickhouse.com/docs/engines/table-engines/integrations/kafka)).
On the producer side, neither OL transport does idempotence or dedup, and the Java
`producer.send()` path is fire-and-forget by default, catching and merely **logging**
exceptions — **lineage loss is silent, at ERROR level only**. Set
`enable.idempotence=true` and `acks=all` in the raw producer props, and rely on
`ReplacingMergeTree` in the archive. Also note Python's `flush: true` **default blocks on
every event**; set `flush: false` for high-volume producers or you serialise the pipeline on
broker round-trips. And under Airflow 2.3–2.6 the Python client creates a **producer per
event** by design ("a Kafka producer needs to be created for each OpenLineage event"),
so expect connection churn.

To pause consumption without losing consumer-group state, `DETACH TABLE
aiops_dq.mv_ol_event_raw; … ATTACH TABLE aiops_dq.mv_ol_event_raw;` — the documented
mechanism.

### 7.2 Macros

Since v4.19.0 the plugin "adopt[ed] grafana/macropro as the macro engine (#1802)" and
v4.20.0 "moved expansion to the sqlds Interpolator extension point (#2008)"
([CHANGELOG](https://github.com/grafana/clickhouse-datasource/blob/v4.21.2/CHANGELOG.md)).
Effective set (`pkg/macros/macros.go`):

| Macro | Expands to |
|---|---|
| `$__dateFilter(col)` | `date >= toDate('2022-10-21') AND date <= toDate('2022-10-23')` |
| `$__timeFilter(col)` | `time >= toDateTime(1415792726) AND time <= toDateTime(1447328726)` |
| `$__timeFilter_ms(col)` | `time >= fromUnixTimestamp64Milli(...) AND time <= fromUnixTimestamp64Milli(...)` |
| `$__dateTimeFilter(dateCol, timeCol)` / `$__dt(...)` | both of the above ANDed |
| `$__timeFrom(col)` / `$__timeTo(col)` | one-sided bound |
| `$__timeGroup(col, '5m')` | `toStartOfInterval(toDateTime(column), INTERVAL 300 second)` |
| `$__fromTime` / `$__toTime` | `toDateTime(1415792726)` / `toDateTime(1447328726)` |
| `$__fromTime_ms` / `$__toTime_ms` | `fromUnixTimestamp64Milli(...)` |
| `$__interval_s` | `20` (whole seconds, floored at 1) |
| `$__timeInterval(col)` | `toStartOfInterval(toDateTime(column), INTERVAL 20 second)` |
| `$__timeInterval_ms(col)` | `toStartOfInterval(toDateTime64(column, 3), INTERVAL 20 millisecond)` |
| `$__conditionalAll(cond, $var)` | `cond`, or `1=1` when the variable is `$__all`/empty |
| `$__adHocFilters('tbl')` | injects filters via `additional_table_filters={...}` |

Plus inherited `macropro` defaults `$__interval`, `$__interval_ms`, `$__table`, `$__column`.

Two details with teeth. **`$__timeFilter` is inclusive on both ends** (`>=` … `<=`), so a
bucket boundary can be double-counted across adjacent panels. And **`$__conditionalAll` is
frontend-only** (`Datasource.applyConditionalAll` in `src/data/CHDatasource.ts`) — it is not
in `ClickHouseMacros`, so it resolves against dashboard variables and is therefore
**meaningless inside an alert rule**, which has no dashboard context.

**Statement macros, new in v4.21.0** (#2019: "add time series statement macros
(`$__columns`, `$__rateColumns`, `$__perSecondColumns`, `$__increaseColumns`, `$__lttb`)"):

```sql
$__perSecondColumns(EventTime, ServiceName, RequestsTotal) FROM requests WHERE ServiceName != ''
$__lttb(auto, EventTime, Latency) FROM requests
```

which generate

```sql
SELECT $__timeInterval(<timeCol>) AS t, toString(<key>) AS <metric>, <valueColumn>
FROM ... WHERE $__timeFilter(<timeCol>) AND (<user WHERE>)
GROUP BY t, <metric>
WINDOW w AS (PARTITION BY <metric> ORDER BY t ASC ROWS BETWEEN 1 PRECEDING AND CURRENT ROW)
ORDER BY t, <metric>
```

with `dt = t - lagInFrame(t, 1, t) OVER w` and `$__perSecondColumns` →
`if(dt = 0 OR delta < 0, nan, delta / dt)`. Constraints per the docs: one statement macro per
query, top level only, they emit their own `GROUP BY` (do not write one), and the first point
of each series and every counter reset are returned as **`nan`**.

`$__lttb(auto|N, x, y)` is server-side largest-triangle-three-buckets downsampling —
genuinely useful and with no Prometheus equivalent.

### 7.3 Alerting

Grafana requires `{"backend": true, "alerting": true}` for a datasource to be an alert-rule
query source; ClickHouse sets both. Practical constraints, from the plugin's
`docs/sources/alerting.md`:

> "Alert rules need numeric values to evaluate. Your ClickHouse query should return data that
> Grafana can use in a **Reduce** expression and then compare in a **Threshold** expression."
> … "Queries that return only text or non-numeric data cannot be used directly for threshold
> evaluation."

and the one that will bite a copy-pasted dashboard query:

> "Ad hoc filters are a dashboard-scoped feature. When Grafana evaluates an alert rule,
> queries run through the backend and ad hoc filters are **not** applied."

Note the asymmetry: ad-hoc filters **are** applied to annotation queries but **are not**
applied to alert queries. Same SQL, two different effective predicates.

**Recording rules.** Grafana-managed recording rules do work against alerting-capable
datasources including ClickHouse, but the core docs are explicit about the catch:

> "Grafana does not contain an embedded time-series database to store recording rule results.
> **You must bring your own Prometheus-compatible database** to store the series generated by
> recording rules."
> — [Create Grafana-managed recording rules](https://github.com/grafana/grafana/blob/main/docs/sources/alerting/alerting-rules/create-recording-rules/create-grafana-managed-recording-rules.md)

They are enabled by default in Cloud and **off by default in OSS**. Also: "Grafana Alerting
only supports fixed relative time ranges, for example, `now-24hr: now`."

So moving to ClickHouse does **not** let you delete Prometheus if you depend on recording
rules — you would keep it purely as a write target. The ClickHouse-native answer is
materialized views, which Grafana knows nothing about: no UI, no lineage, no "this panel
reads a rollup" concept. That precompute layer becomes your team's migration problem rather
than a rule file, which is a genuine operational transfer of cost.

### 7.4 Variables and ad-hoc filters

`src/data/CHVariableSupport.tsx` implements `CustomVariableSupport` with types
`sql | databases | tables | columns | columnValues`. Generated defaults:

```sql
SELECT name FROM system.databases ORDER BY name
SELECT DISTINCT <col> AS value FROM <db>.<t> WHERE <col> IS NOT NULL ORDER BY value LIMIT 1000
-- Map key variant (this is the one you need for OTel Attributes):
SELECT DISTINCT <col>['<key>'] AS value FROM <db>.<t> WHERE mapContains(<col>, '<key>') ORDER BY value LIMIT 1000
```

Note the hard-coded `LIMIT 1000` and the **absence of `$__timeFilter`** — variable queries
are not time-scoped unless you add it yourself. Multi-value needs explicit quoting
(`IN (${database:singlequote})`); the docs warn "Without `:singlequote`, multi-value
variables are comma-separated and can produce invalid SQL", and that cascading multi-value
variables often substitute only the first selected value.

**Ad-hoc filters use the legacy API.** Verbatim from `src/data/CHDatasource.ts` @ v4.21.2:

```ts
async getTagKeys(): Promise<MetricFindValue[]>
async getTagValues({ key }: any): Promise<MetricFindValue[]>
```

`getTagKeys` takes **no arguments at all**. Grafana's newer contract passes
`DataSourceGetTagKeysOptions` / `DataSourceGetTagValuesOptions` carrying `timeRange`, the
already-applied `filters`, and scopes; this plugin ignores all of it. Consequences: key/value
dropdowns are not time-range scoped (a full-table `SELECT DISTINCT ... LIMIT 1000` on an OTel
table), values are not narrowed by other active filters, and the docs confirm "Ad hoc filter
values loaded from the schema are limited to **1000 distinct values** per column."

Other constraints: requires ClickHouse ≥ 22.7 (`adHocCHVerReq = {major: 22, minor: 7}`);
scoping requires a **constant** dashboard variable `clickhouse_adhoc_query` set to `db`,
`db.table`, or a `SELECT`; filters are auto-injected via AST rewriting into the detected
target table, with `$__adHocFilters('tbl')` in a `SETTINGS` clause as the manual escape hatch
for CTEs and subqueries (and its presence disables auto-injection for that query). Operators:
`=`, `!=`, `<`, `<=`, `>`, `>=`, `=~`→`REGEXP`, `!~`→`NOT REGEXP`, `IN`.

**[UNVERIFIED]** Whether Grafana core silently no-ops the newer options argument for a
zero-arg `getTagKeys`, or logs a deprecation — the plugin signature was read; Grafana's call
site was not traced.

### 7.5 Annotations

Supported (`this.annotations = createAnnotationSupport(this)`;
`src/data/CHAnnotationSupport.tsx`; v4.19.0 added a "Preset-driven annotation editor with
change detection (#1922)"). Column contract per `docs/sources/annotations.md`:

| Column | Required | Behaviour |
|---|---|---|
| `time` | yes | marker position, `DateTime`/`DateTime64` |
| `timeEnd` | no | "When present, Grafana draws a **region annotation** … instead of a single vertical line." |
| `text` | yes | hover/click body |
| `title`, tags | no | "Additional columns become annotation tags." |

Region example from the docs:

```sql
SELECT start_time AS time, end_time AS timeEnd,
       concat(window_type, ': ', description) AS text, team AS tag
FROM my_app.maintenance_windows
WHERE $__timeFilter(start_time) ORDER BY start_time DESC LIMIT 100
```

**This is the single most valuable Grafana feature for the DQ half of this design.** A sparse
DQ observation is naturally an annotation, not a series: it renders as a marker on the
existing Prometheus/ClickHouse metric panels, which is precisely the "did this DQ anomaly
coincide with that lag spike?" question answered visually. A column mapping UI means the
column names need not literally match. Caveat: annotation queries "do not use the full
ClickHouse query builder available in panels".

### 7.6 Frame shaping and the OTel gap

Shaping is delegated to `sqlds v5.3.0`. `format` drives
`FormatOptionTimeSeries | Table | Logs | Trace | Multi`; for time series, a **long** frame
(time field + ≥1 string field + ≥1 numeric field) is auto-converted via `data.LongToWide`,
and a zero-row result returns `ErrorNoResults` (which is what makes "No Data" alerting work).
Column contract per `docs/sources/query-editor.md`: alias the timestamp `time`; for
multi-series return `time`, then a group-by column, then metric columns; timestamps without
an explicit zone are treated as **UTC**.

**The finding that matters most for this proposal:** `src/otel.ts` @ v4.21.2 defines

```ts
export const defaultLogsTable = 'otel_logs';
export const defaultTraceTable = 'otel_traces';
```

**There is no metrics table constant, no `otel_metrics_*` handling, and no metrics query
builder anywhere in the plugin.** The "Use OTel" toggle exists only on the Logs and Traces
builders. The bundled dashboards (`plugin.json` `includes`) are Query/Data/Cluster Analysis,
OpenTelemetry Logs Explorer (×2), OpenTelemetry Traces Explorer, OpenTelemetry Service
Dashboard, and ClickHouse System Dashboards — **no metrics dashboard**. OTel metrics in
ClickHouse means hand-written SQL against `otel_metrics_gauge`/`_sum`/`_histogram` with zero
builder assistance and zero schema awareness.

Related, and a good illustration of inherited churn: v4.20.0 had to add OTel schema `1.3.0`
because `clickhouseexporter v0.151.0+` "removed the `TimestampTime` column from `otel_logs`".

### 7.7 Explicit gaps vs Prometheus today

| Capability today (Prometheus) | On ClickHouse | Verdict |
|---|---|---|
| Recording rules (`config/prometheus-rules.yml`) | Grafana-managed recording rules need a Prometheus-compatible write target; native answer is MVs, invisible to Grafana | **Regression** — you keep Prometheus or you own MV migrations |
| `$__rate_interval` | Does not exist. Zero hits for `rate_interval` in the v4.21.2 source | **Regression** |
| `rate()` / `increase()` | `$__perSecondColumns` / `$__increaseColumns`, three weeks old at pin | **Partial, semantically different** — see below |
| `label_values(metric, label)` | `SELECT DISTINCT ... LIMIT 1000`, not time-scoped | **Regression** (scan cost + 1000 cap) |
| Exemplars | "Support for exemplars is available for the Prometheus data source only." Zero `exemplar` hits in the plugin source | **Hard loss** — despite the exporter storing an `Exemplars` Nested column |
| Ad-hoc filters | Legacy zero-arg API, no time/cross-filter narrowing, dropped in alerts | **Regression** |
| Live streaming | No `streaming` flag | **Loss** (probably irrelevant here) |
| PromQL portability | SQL coupled to your exact table schema | **Regression** |
| Arbitrary joins metrics ↔ DQ events | Impossible in PromQL | **Gain — the whole point** |
| Unbounded label cardinality | — | **Gain** |
| `$__lttb` server-side downsampling | — | **Gain** |

Where `$__perSecondColumns` differs from PromQL `rate()`, precisely:

- **Bucket-diff, not sliding window.** `rate()` computes over a lookback window guaranteed
  ≥4× the scrape interval; `$__perSecondColumns` diffs adjacent `$__timeInterval` buckets.
  Zoom in until a bucket holds ≤1 sample and you get `nan`. There is no minimum-samples floor
  in the generated SQL.
- **Counter resets become holes, not corrections.** PromQL adds back the pre-reset value; the
  macro emits `if(dt = 0 OR delta < 0, nan, …)`, so the increment before a restart is lost
  entirely. For a restart-heavy service this **understates** traffic.
- **No extrapolation** to window edges. Arguably more honest, but your existing dashboard
  numbers will change.
- **One key column** (`toString(<key>)`). `sum by (a, b, c)` needs manual `concat()`.
- No staleness markers, no `@`/`offset`, no subqueries, no `histogram_quantile` — histogram
  quantiles over `otel_metrics_histogram` are hand-rolled bucket arithmetic.

**Honest reading of this section.** The DQ half of the proposal lands well on this datasource
— tables, annotations, and full SQL are exactly what sparse event analytics needs, and PromQL
cannot express it at all. The metrics half is where you pay: you would be trading a mature
rate/recording-rule/exemplar stack for hand-written SQL against a table shape the plugin does
not model. That asymmetry drives the recommendation in
[Proposed design](#proposed-design).

## 8. Retention

### 8.1 The four TTL forms

```sql
TTL expr
    [DELETE|RECOMPRESS codec_name1|TO DISK 'xxx'|TO VOLUME 'xxx'][, ...] ...
    [WHERE conditions]
    [GROUP BY key_expr [SET v1 = aggr_func(v1) [, v2 = aggr_func(v2) ...]] ]
```

— [MergeTree](https://clickhouse.com/docs/engines/table-engines/mergetree-family/mergetree)

Three constraints that shape everything below:

- **TTL is merge-time, not wall-clock.** "The deleting or aggregating of expired rows isn't
  immediate — it only occurs during table merges." `merge_with_ttl_timeout` is "the minimum
  delay in seconds before repeating a merge with delete TTL. The default is 14400 seconds
  (4 hours)"
  ([Manage Data with TTL](https://clickhouse.com/docs/guides/developer/ttl)). So "14-day
  retention" means "14 days plus up to ~4 hours, plus merge scheduling". Do not promise
  compliance-grade deletion windows from a TTL alone.
- **`GROUP BY` TTL: "GROUP BY expression must be a prefix of the table primary key."** Not a
  suggestion. If you want to roll up by `(id, day)` then `(id, day)` must prefix the key.
- **`ttl_only_drop_parts = 1`** makes expiry a whole-part drop instead of a row-level rewrite.
  The exporter already sets it in the default metrics DDL (§1.2) — keep it, and make sure the
  partition granularity matches the TTL granularity or it does nothing useful.

### 8.2 Dense metrics — short raw retention, rolled up, tiered

The exporter's `ttl:` config can only produce `TTL TimeUnix + toIntervalDay(N)` (§1.1). Every
technique below requires `create_schema: false`.

```sql
-- Raw: 14 days on hot storage, then gone. Daily parts + ttl_only_drop_parts = cheap drops.
ALTER TABLE otel.otel_metrics_sum
    MODIFY TTL
        TimeUnix + INTERVAL 3 DAY  TO VOLUME 'warm_volume',
        TimeUnix + INTERVAL 14 DAY DELETE;
```

with the storage policy from the TTL guide (`/etc/clickhouse-server/config.d/storage.xml`):

```xml
<clickhouse>
  <storage_configuration>
    <disks>
      <hot_disk><path>./hot/</path></hot_disk>
      <warm_disk><path>./warm/</path></warm_disk>
      <cold_disk><path>./cold/</path></cold_disk>
    </disks>
    <policies>
      <default>
        <volumes>
          <hot_volume><disk>hot_disk</disk></hot_volume>
          <warm_volume><disk>warm_disk</disk></warm_volume>
          <cold_volume><disk>cold_disk</disk></cold_volume>
        </volumes>
      </default>
    </policies>
  </storage_configuration>
</clickhouse>
```

Downsampling is where you get long metric history without long metric cost. Two ways:

**(i) MV + `AggregatingMergeTree` (preferred — the source table stays untouched):**

```sql
CREATE TABLE otel.metrics_sum_5m
(
    bucket       DateTime               CODEC(Delta, ZSTD(1)),
    service_name LowCardinality(String) CODEC(ZSTD(1)),
    metric_name  LowCardinality(String) CODEC(ZSTD(1)),
    topic        LowCardinality(String) CODEC(ZSTD(1)),
    v_avg        AggregateFunction(avg, Float64),
    v_max        SimpleAggregateFunction(max, Float64),
    v_min        SimpleAggregateFunction(min, Float64),
    v_q          AggregateFunction(quantilesTDigest(0.5, 0.95, 0.99), Float64),
    n            SimpleAggregateFunction(sum, UInt64)
)
ENGINE = AggregatingMergeTree
PARTITION BY toYYYYMM(bucket)
ORDER BY (service_name, metric_name, topic, bucket)
TTL bucket + INTERVAL 180 DAY DELETE
SETTINGS ttl_only_drop_parts = 1;

CREATE MATERIALIZED VIEW otel.mv_metrics_sum_5m TO otel.metrics_sum_5m AS
SELECT
    toStartOfInterval(TimeUnix, INTERVAL 5 MINUTE)            AS bucket,
    ServiceName                                                AS service_name,
    MetricName                                                 AS metric_name,
    Attributes['messaging.destination.name']                   AS topic,
    avgState(Value)                                            AS v_avg,
    max(Value)                                                 AS v_max,
    min(Value)                                                 AS v_min,
    quantilesTDigestState(0.5, 0.95, 0.99)(Value)              AS v_q,
    toUInt64(count())                                          AS n
FROM otel.otel_metrics_sum
GROUP BY bucket, service_name, metric_name, topic;

-- read side
SELECT bucket, service_name, topic,
       avgMerge(v_avg) AS v, max(v_max) AS v_max,
       quantilesTDigestMerge(0.5, 0.95, 0.99)(v_q) AS q, sum(n) AS n
FROM otel.metrics_sum_5m
WHERE metric_name = 'kafka_consumergroup_lag' AND bucket >= now() - INTERVAL 30 DAY
GROUP BY bucket, service_name, topic;
```

Note the deliberate mix: `SimpleAggregateFunction` for min/max/sum (cheap, no `-Merge`
needed at read time beyond the plain aggregate) and `AggregateFunction` only where the state
is genuinely required. And note the `-State`-versioning caveat from §4.4 — acceptable here
precisely *because* this table is regenerable and capped at 180 days.

**(ii) In-place `TTL … GROUP BY` rollup** — for when you want one table, not two. The doc's
own example:

```sql
CREATE TABLE hits (
  timestamp DateTime,
  id String,
  hits Int32,
  max_hits Int32 DEFAULT hits,
  sum_hits Int64 DEFAULT hits
)
ENGINE = MergeTree
PRIMARY KEY (id, toStartOfDay(timestamp), timestamp)
TTL timestamp + INTERVAL 1 DAY
    GROUP BY id, toStartOfDay(timestamp)
    SET max_hits = max(max_hits), sum_hits = sum(sum_hits)
```

Observe how the DDL is *shaped by* the prefix rule: `PRIMARY KEY (id, toStartOfDay(timestamp),
timestamp)` exists so that `GROUP BY id, toStartOfDay(timestamp)` is a legal prefix. **You
cannot bolt `TTL … GROUP BY` onto the exporter's default metrics table**, whose key is
`(ServiceName, MetricName, toStartOfHour(TimeUnix), cityHash64(Attributes), TimeUnix)` — a
rollup prefix of `(ServiceName, MetricName, toStartOfHour(TimeUnix))` would collapse *all
attribute sets together*, silently merging every topic's lag into one number. This is a
concrete, checkable reason the sort key must change if you want in-place rollup, and it is why
recommendation (i) is preferred.

Conditional retention also works, and maps onto the existing findings model:

```sql
TTL TimeUnix + INTERVAL 14 DAY  DELETE WHERE ServiceName != 'aiops-hot-path',
    TimeUnix + INTERVAL 90 DAY  DELETE WHERE ServiceName  = 'aiops-hot-path'
```

### 8.3 Sparse DQ observations — long retention, no rollup, tiered

```sql
ALTER TABLE aiops_dq.dq_observation
    MODIFY TTL
        observed_at + INTERVAL  90 DAY TO VOLUME 'warm_volume',
        observed_at + INTERVAL 365 DAY TO VOLUME 'cold_volume',
        observed_at + INTERVAL 730 DAY DELETE;

ALTER TABLE aiops_dq.dq_assertion
    MODIFY TTL
        observed_at + INTERVAL  90 DAY TO VOLUME 'warm_volume',
        observed_at + INTERVAL 365 DAY TO VOLUME 'cold_volume',
        observed_at + INTERVAL 730 DAY DELETE;

-- Archive: longest of all, and recompressed hard rather than rolled up.
ALTER TABLE aiops_dq.ol_event_raw
    MODIFY TTL
        event_time + INTERVAL  30 DAY RECOMPRESS CODEC(ZSTD(12)),
        event_time + INTERVAL 180 DAY TO VOLUME 'cold_volume',
        event_time + INTERVAL 1095 DAY DELETE;
```

**No `GROUP BY` rollup on the DQ side, deliberately.** Rolling up a DQ observation destroys
the thing that makes it valuable: it is an *audited fact* tied to a `run_id` and a
`facet_schema_url`. `SET value = avg(value)` would produce a number that no run ever
produced, breaking the replay property the repo already commits to for casefiles. Retention
here is a compression and tiering problem, not an aggregation problem. `RECOMPRESS
CODEC(ZSTD(12))` on the raw JSON archive is the right lever — the data is highly repetitive
JSON, so the ratio is excellent, and nothing ever queries it on the hot path.

Column-level TTL is a cheaper middle ground if the archive gets large — drop the fat payload
while keeping the skinny identity columns forever:

```sql
ALTER TABLE aiops_dq.ol_event_raw
    MODIFY COLUMN payload String TTL event_time + INTERVAL 400 DAY;
```

After 400 days the row still exists (you can still prove a run happened, with its job and
run id); only the payload blob is gone. Whether that trade is acceptable is a governance
question, not a technical one — flag it for the review.

|---|---|---|---|
| `otel_metrics_*` (raw) | `toDate(TimeUnix)` | 1 | 3d → warm; 14d DELETE |
| `metrics_sum_5m` (rollup) | `toYYYYMM(bucket)` | 1 | 180d DELETE |

## Proposed design

### Shape of the recommendation

**Phased, and the phases are separable on purpose.** The DQ half of this proposal is a clear
win. The metrics half is a real trade with real regressions ([§7.7](#77-explicit-gaps-vs-prometheus)).
Do not couple them.

| Phase | Scope | Prometheus | Decision gate |
|---|---|---|---|
| **1** | ClickHouse for **OpenLineage DQ only**. Kafka → CH. DQ rendered as Grafana **annotations** over existing Prometheus panels. | unchanged | Are DQ observations actually arriving and useful? |
| **2** | Add `entity_map` + cross-signal queries. Metrics **still** in Prometheus; correlate by exporting only the specific metric series you need into `metrics_sum_5m` via the collector's `clickhouseexporter` alongside the existing `prometheus` exporter. | unchanged (dual-export) | Is anyone writing the ASOF/bucket joins? |
| **3** | Only if Phase 2 proves the join is load-bearing: migrate metric dashboards/alerts. | retained as recording-rule target | — |

Phase 1 delivers most of the value ("did this DQ anomaly coincide with that lag spike?"
answered visually) at a fraction of the risk. Phase 3 is the expensive one and should have to
earn its way in. Note that Phase 2's dual-export is cheap — a collector metrics pipeline can
fan out to two exporters — and it is what makes Phase 3 optional rather than inevitable.

## Open questions / risks

### Risks, ranked by how likely they are to sink the project

**R1 — There is no OpenLineage producer in this repo today.** Everything in §2/§6 assumes
someone emits OL events. This pipeline is Python + Kafka + Postgres; there is no dbt, no
Spark, no Airflow, and dbt/Great Expectations are the realistic in-tree producers of the DQ
facets (`integration/common/.../dbt/processor.py`,
`.../great_expectations/action.py`). **The most likely outcome of adopting this design is an
empty `dq_observation` table.** Before any DDL, answer: what emits the first event, and does
it emit `DataQualityMetricsInputDatasetFacet` or does someone have to write a custom facet?

**R2 — The metrics exporter is `alpha` and has broken its schema before.** `alpha` explicitly
permits breaking changes; two metrics-table breaks are on the record (v0.98.0, v0.104.0), and
the current metrics `ORDER BY` appears to have changed *without* a breaking-change note
(§1.4). Mitigation: `create_schema: false`, vendored DDL, and a CI job that diffs
`internal/sqltemplates/*.sql` at the pinned tag against your migrations on every collector
bump. This mitigation must be built, not assumed.

**R3 — Grafana has no OTel *metrics* support in the ClickHouse datasource.** `src/otel.ts`
@ v4.21.2 defines only `otel_logs` and `otel_traces`; there is no metrics builder and no
metrics dashboard (§7.6). Every metric panel is hand-written SQL. Combined with the loss of
`$__rate_interval`, exemplars, and PromQL-semantics `rate()`, this is the strongest argument
for keeping Phase 3 optional.

**R4 — `entity_map` has no owner and will rot.** It is hand-curated, it is the thing that
makes this "one system" (§5.6), and it silently produces *wrong* joins rather than errors when
stale. Worse, the OL Kafka namespace embeds *one* bootstrap host, which is not a stable
cluster identity. Mitigation: put it in migrations, add a scheduled query that reports
`dq_observation` rows with no `entity_map` match, and alert on it.

**R5 — `max_dynamic_paths` will be exceeded if the native `JSON` type is used for OL
payloads.** A 200-column dataset generates ~1200 `columnMetrics.*` paths on its own against a
default of 1024; overflow spills to a shared structure whose reads "require scanning the
entire shared data structure" (§2.1). The proposed design avoids this by using `String` +
extraction for the archive, but anyone "improving" it to `JSON` reintroduces the problem.

**R6 — Baseline nondeterminism vs the replay guarantee.** `quantileTDigest`'s "result depends
on the order of running the query, and is nondeterministic" (§4.2) conflicts with
`docs/schema-evolution-strategy.md`'s auditor-replay story. Mitigated by `dq_baseline`
materialising ordinary numbers with a `baseline_version`, but only if the gate actually reads
that table instead of recomputing.

**R7 — At-least-once everywhere, and one silent-loss path.** The ClickHouse Kafka engine is
at-least-once (offsets commit after MV delivery; the docs advise `fsync_after_insert = 1`),
and the OL Java transport's `producer.send()` is fire-and-forget, catching exceptions and
**only logging at ERROR** — lineage loss is silent. Set `enable.idempotence=true` /
`acks=all`, keep the DLQ table, and monitor it.

**R8 — Hot-job partition skew.** The OL message key is per-**job**, not per-run
(`run:{ns}/{name}` — §6.4), so one busy job pins one partition. Also note the upstream doc's
`*Notes*` block is stale and claims a run id is in the key; anyone sizing partitions from the
docs rather than the source will get this wrong.

**R9 — TTL is merge-time.** "14-day retention" is 14 days + up to `merge_with_ttl_timeout`
(default 4h) + merge scheduling. Do not write a compliance commitment against a TTL clause.

**R10 — Operating a new stateful system.** ClickHouse joins Postgres, Redis, MinIO, Kafka,
Prometheus, and Grafana in the compose stack. Backups, upgrades, disk tiering volumes, and
`system.query_log` retention are all new operational surface not currently owned by anyone.

### Open questions for the review

1. **What emits OpenLineage events?** (R1.) If the answer is "we'd write a custom emitter in
   the pipeline", then the DQ facets are ours to define and the spec-fidelity work in §2 is
   partly optional — which changes the recommendation materially.
2. **Is the join in §3 actually going to be written by a human?** If the real requirement is
   the Grafana annotation overlay, stop at Phase 1 and never migrate metrics.
3. **Two years of DQ retention — is that a governance requirement or a guess?** It drives
   tiering, disk provisioning, and whether the column-level payload TTL (§8.3) is acceptable.
4. **Who owns `entity_map`?** Name a person or the design does not hold.
5. **Single node or cluster?** Everything above is single-node DDL. `Replicated*` engines and
   `ON CLUSTER` change the migration story, and the exporter has a `cluster_name` option that
   injects `ON CLUSTER`.
6. **Do we keep Prometheus permanently?** §7.3 says yes if recording rules matter — Grafana
   recording rules still need a Prometheus-compatible write target. That reframes this from
   "replace Prometheus" to "add ClickHouse", which is a different budget conversation.

### Claims I could not verify from a primary source

- **Metrics `ORDER BY` provenance.** No changelog entry announces the current metrics sort key
  including `toStartOfHour(TimeUnix)` / `cityHash64(Attributes)` (§1.4).
- **`Object('json')` deprecation wording.** No doc page states it in those words; the evidence
  is the `MAKE_OBSOLETE` block in `Settings.cpp` plus the doc redirect (§2.1).
- **Whether `ALTER TABLE ADD COLUMN … MATERIALIZED` backfills existing parts.** The CREATE
  TABLE docs do not address it (§2.1).
- **Any ASOF tolerance/`WITHIN` clause.** None found in the JOIN docs; post-filtering on the
  computed skew is the mechanism (§3.3).
- **The example `mv_dq_observation` SQL is illustrative, not executed** (§6.8). The chained
  `ARRAY JOIN` over `JSONExtract*Raw` is the right shape; exact spellings need validation on
  your server version.
- **`toStartOfInterval` reference page.** Used throughout; the canonical date-time function
  page did not render the entry via fetch. Semantics (including the `origin` overload) are
  confirmed from the [ClickHouse v24.10 changelog](https://clickhouse.com/docs/changelogs/24.10).
- **`transports-kinesis` config keys** — module exists in the OL Java tree, zero docs at
  1.53.0.
- **Marquez `SEARCH_ENABLED` backing store.**
- **Whether Grafana core no-ops or warns** on the plugin's zero-arg `getTagKeys` (§7.4).
- **Third-party (non-first-party) OL→ClickHouse projects.** The "none exists" claim in §6.7 is
  scoped to first-party: the OpenLineage org, the Marquez org, and the official ecosystem
  consumers list.
- **`WITH FILL` + `GROUP BY` interaction.** One fetched summary asserted `WITH FILL` "cannot
  combine with `GROUP BY`"; this contradicts the ordinary reading that `ORDER BY … WITH FILL`
  runs after aggregation, so the claim is **not** repeated as fact anywhere in this document.
  Verify empirically before relying on §4.3.

    Appendix

      The ask

      Extending baseline anomaly detection to data-quality signal

      We detect that the pipe broke. We detect nothing about what the pipe was carrying. This is a proposal to change that, and to prove it on a path we own end to end.

      I'm asking for one thing today: agreement on the direction. Data-quality and infrastructure signal converge into one triaged case. Detection starts in Snowflake, where the data lives, and the seam that lets it move into our own store gets built now rather than promised.

      Two facts before anything else, because they change what kind of conversation this is:

      • Nothing here is blocked on another team. The proving run lives in E2's own Snowflake space, monitored by our own dbt project, correlated against metric series we already collect. We can build all of it without anyone's permission.
      • The first deliverable is a cost probe, not the pipeline. Days of work, and it converts our largest unknown into a number before we ask anyone for anything.

      And nothing here is live, so every contract in this proposal is a design choice rather than a migration.

      This generalises to the whole medallion. I'm not asking for that today — the picture is here whenever you want it.

      The problem

      We detect the pipe, never the payload

      We detect anomalies in operational metric series — Kafka consumer lag, throughput — and turn them into triaged cases. We detect nothing about the data those topics carry.

      The failures that actually reach consumers are usually not "the broker was down". They are:

      "the table has a third of yesterday's rows"
      "a column went null"
      "the load never ran"

      Today those are found by a consumer noticing — which means the blast radius is already downstream, and the person who notices is the person least able to fix it.

      The problem, second half

      Cause and impact arrive as two unrelated observations

      Even where data-quality checks exist as dbt tests, their results live in a different system from the operational signal, keyed differently, read by different people.

      A stalled consumer group and the short load it caused are one incident. They arrive as two unrelated observations — or as one observation and a silence.

      What we want is that both kinds of signal land in the same triaged case, keyed so the responder sees the cause and the impact together.

      The destination

      What one case looks like

      The first of six scenarios we intend to inject. Concretely, end to end:

      1. 02:14 – 02:58  A consumer group stalls. Lag climbs, throughput drops — two co-deviating metric series in one Kafka scope. The detector raises a finding today. It has nowhere to go. The deviating cycles collapse into one episode with a first and last time, which is new: today each cycle would be its own finding.
      2. 03:00  The 02:00 hour closes. The landing table took a third of its usual rows for that hour.
      3. 03:05  The hourly dbt test runs. The 02:00–03:00 bucket is complete, so Elementary scores it and writes a measurement and a verdict. The bucket now filling is ignored — a half-filled hour always looks short.
      4. 03:12  The pipeline reads that verdict and raises a DQ finding in our own vocabulary: volume, not Elementary's test name.
      5. The declared source mapping links that landing table back to the topic. That is the join. Dataset identity and topic identity share nothing, and time alone would correlate every dataset with every lag spike.
      6. Only then does time filter the candidates: the measurement's own interval, extended back by half a bucket — 01:30 – 03:00. The episode 02:14 – 02:58 overlaps it.
      7. One case, 12 minutes after the hour ended — and at worst 75, if the bucket closes just after a test run rather than just before. Root: the infrastructure scope. The dataset anomaly attaches as impact rather than opening a case of its own. Severity is derived — from how close the root sits to consumers, and from the size of the blast radius.

      Today

      A lag alert nobody connects to anything, and a short table nobody notices until a consumer complains.

      After

      One case, carrying the cause, the impact, the measurement curve with its expected range, and the dbt checks that failed in the same run.

      The one new component

      Elementary, in one screen

      It is a dbt package, and its monitors are dbt tests. That single fact is most of why this proposal is cheap.

      • It writes a time-bucketed measurement history (data_monitoring_metrics) and verdicts (elementary_test_results) into tables it builds itself.
      • Measurements are produced where the data lives, by the same dbt run that builds the data.
      • So adding it needs no new detection infrastructure — only an egress path and a contract.

      What we take from it: volume, null rate, freshness. What the triage pipeline then does is the part only it can do — link the dataset back to the source, correlate with operational anomalies in the same window, decide the root, gather the blast radius, derive severity, and route.

      Elementary also stores whole raw failing rows. We never read them — what the pipeline is allowed to read.

      v1

      A proving run on a path we own end to end

      E2 sits outside the medallion. It owns a repository and a Snowflake space holding the landing table its topic data arrives in and the consumer table it exposes for reading. v1 runs entirely there — three nodes, all ours, mimicking at small scale the downstream movement the medallion performs at large scale.

      Neither hop is a daily batch. The topic streams into the landing table continuously; a separate job copies landing into the consumer table every 15 minutes. So the chain is exercised every hour rather than once a day — and the consumer table carries the landing row's load timestamp through rather than restamping, so both tables bucket on the same clock and a catch-up refills the hour that was short instead of showing up as a spike in the next one.

      No downstream consumer reads that consumer table. So this is a proving run, not a pilot — and the difference matters for what we're allowed to claim. It can prove the mechanism end to end, the cost, the correlation rate and the false-positive behaviour. It cannot prove that incidents were caught before a consumer reported them, and we don't claim it.

      What we get in exchange: we control both ends, so we inject the failures instead of waiting for them. That produces evidence in week four rather than week sixteen.

      The one structural change

      The seam gets built in v1

      The baseline detector's mathematics is series-agnostic. Everything around it is not — it was shaped by its only user.

      So we rebuild it against a seam one level lower: a baseline is computed over a series identity plus the observation's own time, with cadence, bucketing, minimum history and gating treated as properties of the series kind.

      That reframing is what lets an hourly DQ measurement series and a 300-second metric series share a detector at all — and a once-daily IDP series after them, without a third code path. We build it in v1 even though v1 detects data-quality anomalies in Snowflake, because metric series move to ClickHouse in v1 regardless — the storage layer is being touched anyway, and nothing is live.

      Those properties are declared in one series-kind registry, not scattered across the tools that read them. That is what makes "registering a second series kind" the real shape of the work later, rather than a figure of speech.

      Bucket width follows a rule, not a preference. The smallest shortfall a volume monitor can see is about one load unit spread over the bucket. The consumer table is copied every 15 minutes, so an hourly bucket holds four and one failed copy is a 25% drop. A daily bucket would hold ninety-six, and the same failure would be a 1% drop — invisible. A once-daily IDP load gets daily buckets by the same rule.

      The before-and-after, and what the current abstraction wrongly assumes: the seam in full (ADR-0001).

      Where the difficulty actually is

      Three things that are genuinely hard

      1. Linking a dataset back to its source

      Correlation needs an entity link, and dataset identity shares nothing with topic identity. The hop from source → landing table is recorded by no tool in our stack. We declare it in a source mapping. Time co-occurrence alone was rejected: it would correlate every dataset with every lag spike in the same window.

      2. Root dataset and blast radius

      Because data flows downstream, one upstream problem surfaces everywhere below it. So a dataset-keyed case is keyed on the root dataset — the most upstream monitored dataset anomalous in the window. Anomalies below it attach as blast radius rather than opening cases of their own.

      The word monitored is load-bearing. A defect introduced where nothing is monitored surfaces as a root further downstream than its true cause, so a case whose root has a clean monitored ancestor is marked transform-suspected and is not attributed to the root's owner. How often that happens is something the proving run measures — it's the evidence for how much lineage coverage v2 needs.

      3. Silence

      Detection inside the pipeline cannot see the pipeline stopping. If a job never runs, Elementary produces no verdict and no measurement — the quietest failure mode produces the quietest signal. So silence is a first-class finding raised by the triage pipeline, from the set of series we expect to produce.

      Cadence for the v1 set is declared, not learned. Learned cadence was our first instinct and it is blind exactly where silence matters most: a series that has never produced has nothing to learn from, so a dataset whose load never runs at all would be invisible.

      The decision

      Detect in Snowflake now. Our own detector as the target.

      Both options put metric series in ClickHouse. They differ on one axis: where data-quality detection runs.

      Option C — now

      Elementary judges, inside the dbt run. Measurements stay where they're produced. No copy, because the series already exist where the data lives.

      Option A — the target

      Our own baseline detector judges. Measurements are copied into ClickHouse. Raw curves natively; any measurement producer, not just dbt.

      We move to A when any one of these becomes true: Elementary's z-score proves too noisy to triage; correlation needs the raw curves rather than verdicts; or a producer of measurements outside dbt appears that Elementary cannot see.

      Three things keep that door genuinely open rather than nominally:

      • The finding vocabulary uses our own DQ families — volume, null rate, freshness, silence — not Elementary's test names, so the contract survives the switch.
      • Curve polling in C is a rehearsal of A.
      • The seam is built in v1, so A is the registration of a second series kind rather than a refactor we'd have to find appetite for at the exact moment we were unhappy with the detector.

      The evidence bar

      How we would know it worked

      We own both ends of this path, so we inject the failures rather than waiting for them. The headline measure is scenario coverage — six scenarios, each with an expected case shape:

      1. Consumer group stalls, the hour's rows land short → one case, infrastructure root, dataset anomaly merged.
      2. A monitored column starts arriving null → one case, dataset root, no correlated cause.
      3. The copy job stops entirely → a silence finding, not a freshness anomaly. A single missed copy is injected separately: an hourly bucket sees that as a 25% volume shortfall, not silence.
      4. A late-arriving backfill → no case.
      5. A legitimate business volume spike → a case dispositioned benign-real, not wrong.
      6. A cluster-wide stall across more than five scopes → one storm case with children attached.

      The last two carry the most weight: a detector is proven as much by what it declines to raise as by what it raises.

      These thresholds are committed now, before the numbers exist. I'm not asking you to ratify them — I'm asking whether any of them is obviously wrong.

      MeasureCommitted rule
      False positivesNo more than one wrong case per dataset per week, sustained. If we miss it, the response is Option A or revisited sensitivity — not suppression.
      CostUnder 2% of the warehouse's existing daily credits, proceed. 2–10%, proceed and carry a per-table cost table into the platform ask. Above 10%, retune and re-probe before asking anyone for anything.
      Correlated shareAbove 30%, correlation stays the headline claim. 10–30%, reframe as one triage surface with correlation where it exists. Below 10%, the case merge doesn't pay for the declared graph's upkeep.

      Every case gets a human disposition — actionable, benign-real, or wrong. One named person, one pass a day, for the duration: a real recurring cost, and the instrument that produces the evidence. A two-way pass/fail would hide the benign-real class and push us to detune a detector that is working.

      Two gates

      Elementary's cold start has two halves, weeks apart. Hourly bucketing shortens the first one sharply: a non-seasonal baseline gates on min_training_set_size (default 7), which on an hourly series is seven complete hours — not the two weeks a daily series would need. Seasonal comparison still takes roughly fourteen weeks, because hour_of_week seasonality multiplies days_back by seven and each seasonal bucket gains one sample per week.

      • Gate 1, ~4 weeks: cost number, scenario coverage, mechanism end to end, seam built. The go/no-go — and what comes back to you.
      • Gate 2, ~16 weeks: sustained false-positive rate, correlated share, transform-suspected share, seasonal comparison live.

      Any false-positive number before Gate 2 is indicative, not deciding.

      One thing to flag, not to decide today. After Gate 2 we'll ask the dbt platform team to carry a standard monitor set and our read grants in its tenant template. Every request has a fallback, so none of them blocks v1 — but it's an organisational conversation, and it goes better pre-socialised than cold. The full list of requests.

      Nobody outside the triage team gets paged, for now — why.

      Appendix B

      The seam in full (ADR-0001)

      The baseline detector computes a modified z-score over MAD against seasonal buckets held in Redis, rebuilt weekly from Prometheus. The mathematics is series-agnostic. Everything around it is not:

      • Buckets derive from the hot-path cycle time rather than from the observation's own timestamp.
      • Bucketing is fixed at hour-of-week for every series.
      • Zero-variance series are silently skipped.
      • A finding requires two co-deviating metrics in a scope.
      • Scope identity is built from Prometheus labels and rejects anything without env, cluster_id and topic.
      • Severity is hard-coded.
      • The finding vocabulary is a closed set of Kafka families.

      We state that plainly rather than claiming the abstraction generalises — it was shaped by its only user. The seam sits one level lower: a baseline is computed over a series identity plus the observation's own time, with cadence, bucketing, minimum history and gating treated as properties of the series kind.

      Nothing is live, so the hot path is rebuilt against the seam rather than migrated behind it. Building it in v1 is what turns Option A from a migration into the registration of a second series kind.

      Two related contract changes

      One anomalous measurement raises a finding. The metric path's two-series corroboration gate exists because a lone noisy Prometheus series means little. A dataset may carry one monitor, and requiring corroboration would discard most of the signal this proposal exists to catch. Corroboration instead raises severity.

      A metric finding is an episode, not a sample. Correlation needs the metric side to have a time extent, and today it has none: Prometheus is read with instant queries only, grouped by scope with no time dimension. A forty-minute stall produces one finding per cycle, each an instant. So consecutive deviating cycles collapse into one deviation episode with first_seen and last_seen.

      The reason is the evidence bar, not elegance. A deviation from 02:40 to 03:20 against a window ending 03:00 puts four cycles inside and five outside — one incident becomes four correlated fragments and five orphans. Correlated share is a number we commit to at Gate 2, and it has to count incidents rather than move with scheduler alignment.

      Appendix C

      What it costs

      Elementary's monitors are dbt tests: they run in a warehouse, on someone's credit. For the proving run that someone is us. For the medallion it would be each tenant — a real fact to put in front of you rather than hide.

      We have no credit estimate, no published benchmarks exist, and any number we invented would be a guess dressed as evidence. So the first deliverable is a cost probe: Elementary on the proving run's tables with the standard monitor set and a timestamp_column present, measured in credits from QUERY_HISTORY and extrapolated per table per day. It also doubles as the history warm-up the cold start needs anyway.

      The four knobs that decide the number

      KnobWhy it matters
      timestamp_columnNo default. Without one: full table scan every run, one point per run, no freshness monitor, and bucket_start is NULL — which leaves correlation nothing to key on. Must be a load timestamp, not a business event timestamp.
      time_bucketHourly multiplies rows ~24× against the daily default, and hour is the finest period Elementary offers. Not a free knob: it is part of the identity Elementary keys stored history on, so changing it forks the history and forces a full days_back recompute. Settled before the probe, not after.
      MaterialisationBucket reuse applies only to dbt sources and incremental models. A table-materialised model recomputes its whole training window every run.
      Monitor setall_columns_anomalies issues two queries per column. The standard set uses column_anomalies on key columns instead.
      CoverageWhich tables are monitored at all.

      Both options put metric series in ClickHouse. Greenfield makes that a platform choice rather than a migration, and it removes the weekly Prometheus rebuild of Redis buckets, since history then lives in the table.

      Option B — data quality in Snowflake, metrics in ClickHouse, two detectors, no shared contract — was considered and dropped: it is C with the correlation goal abandoned.

      Why curve polling is mandatory, not enriching

      A passing test does not close a case. An Elementary anomaly test fires only while the bad bucket is inside backfill_days (default two) and then silently returns to pass, whether or not anything was fixed. A case closes when the series produces in-range measurements for three consecutive buckets, or when a human resolves it — and an absent measurement is silence, not recovery, so auto-close never fires on a bucket Elementary did not write.

      "In range" is observable only from data_monitoring_metrics, never from verdicts. Reading curves is therefore load-bearing in Option C — which tilts the cost balance toward Option A by more than the original framing suggested.

      Appendix E

      What the pipeline is allowed to read

      Elementary stores up to five whole raw failing rows per ordinary dbt test in test_result_rows. Those are real business records and may contain personal data, and our pipeline writes casefiles to MinIO, outside Snowflake.

      The claim: the triage pipeline holds counts, rates and timings about data, never field values.

      "Aggregates, never the data" would be too loose to defend — min/max on a column is an aggregate and a value from a real record. Concretely:

      • Grant the pipeline's role USAGE on database and schema and SELECT table by table, excluding test_result_rows.
      • Propose test_sample_row_count: 0 so samples are never collected.
      • Keep dimension_anomalies and freshness's raw timestamp fields out of the monitor set.
      • Enable column_anomalies monitor types by name, excluding min, max, min_length and max_length.

      That costs little detection power, because every failure in the problem statement is a count, a rate or a timing.

      On the multitenant platform this is not a single grant — each tenant's Elementary tables live in that tenant's own space, so SELECT belongs in the tenant template rather than in a conversation per team. Otherwise coverage stops depending on who adds monitors and starts depending on who grants access, which is the same failure wearing a different hat.

      One caveat for whoever implements it: Elementary's sample-gating flags are mostly undocumented and were found by reading its source, so they need verifying against the installed version.

      Appendix F

      Who gets paged

      Nobody outside the triage team, for now. Monitors applied by convention plus routing to dataset owners would page teams that asked for nothing, from a detector whose error rate we cannot yet state — the fastest way to get the whole thing muted.

      Every case routes to us; we disposition and hand off by hand. Owner routing is a later step gated on the false-positive bar, which is also the moment data owners need to be told the system exists.

      Above everything: the storm case

      A cluster-wide incident makes every topic anomalous and every landing table short at once. Without a rollup that is hundreds of cases describing one event. Above five co-firing scopes in one cluster, they become one storm case with the scope cases as children, notifying once.

      Appendix G

      Why not OpenLineage, and why not Cortex

      OpenLineage

      It was the research's starting point as the carrier for data-quality signal, and it carries less than we need: column-level distributions have no first-party producer outside Great Expectations, streaming ingestion emits no statistics facets, and the Spark–Snowflake connector probably never fills the output counters we would read. Manual emission is real and cheaper than expected at platform level — but dbt has no extension point at all, and emitting a measurement means measuring it ourselves, which is Elementary's job.

      So v1 takes no OpenLineage dependency. It remains the convergence path for lineage, on our own schedule, and publishing our declared source mapping as OpenLineage events is a stated bonus: it fills an ingestion hop the org's lineage tooling also lacks.

      Snowflake Cortex ANOMALY_DETECTION

      Researched as a detector; an evaluated upgrade path, not v1. It is better statistics than a z-score, but it needs explicit models, manual retraining, and the same egress problem — and it would bind detection harder to Snowflake at exactly the moment the stated target is to move detection out.

      Appendix H

      Verdict egress

      The pipeline re-reads a bounded 48-hour window every 15 minutes and deduplicates, rather than advancing a watermark. Three verified facts rule the watermark out:

      • Elementary's result tables are append-only with no purge.
      • created_at is recorded in session timezone, unlike its sibling columns.
      • id values repeat.

      A cursor over a column that is neither monotonic nor timezone-stable drops rows silently, which is the worst available failure mode here. Ingestion is idempotent by construction, so re-reading is free correctness. A daily reconciliation compares verdict counts in Snowflake against findings ingested, because we cannot detect our own silence.

      A case therefore exists within an hour of a verdict being written. Total latency is set by bucket width and test cadence — not by this pipeline, and not by the load cadence. The bucket has to close, the next dbt test has to run, and the poll has to come round: on E2's hourly series that is a case within 75 minutes of the end of the hour the shortfall happened in — twelve if the bucket closes just before a test run, seventy-five if just after. On a daily IDP series it is a day, because a daily bucket cannot close sooner.

      The monitoring project therefore runs one schedule per cadence tier, selected by tag. A single hourly run across daily-bucketed series would recompute the same two buckets twenty-four times a day for no new information.

      The bucket that has not closed

      A measurement for the hour currently filling describes a partial hour, which Elementary scores against complete ones and finds a shortfall that does not exist — one false verdict per series per run, every run, self-healing an hour later when backfill_days recomputes the finished bucket. Against a bar of one wrong case per dataset per week, that alone would miss by two orders of magnitude.

      So the pipeline ignores any verdict or measurement whose bucket_end is in the future. It sits in the bounded-window read, and it is safe there because bucket_end — unlike created_at — is timezone-stable. One predicate, three readers: finding ingest would raise the false verdict; auto-close would count a half-filled bucket that happens to read in-range toward its three and close a live incident early; silence would fire for every series for the duration of its current bucket. Elementary's detection_delay helps only the first, and its boundary behaviour is undocumented — so it stays a cost question for the probe, not a correctness mechanism.

      Repeat verdicts on an open case attach as recurrences, deduplicated on Elementary's own key; its own suppression state is an edr CLI feature invisible to a table reader, so deduplication is ours.

      Open question, a spike rather than a dependency: a Snowflake Python stored procedure writing to Kafka directly would remove the poller entirely. The Snowflake Kafka connector is ingest-only, so this is the only outbound-to-Kafka shape available.
